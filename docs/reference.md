# Aureal Vortex 2 (AU8830) hardware reference

Last updated 2026-11-16 · [Z2k Retro](https://github.com/z2k-retro) · see [the appendices](README.md) for data, formats and procedures

## Purpose and status

This is a reverse-engineering reference. Aureal never published register-level documentation for the Vortex 2, and nothing here comes from its source code or internal documents. It records what a real card was observed to do, so that anyone can build an emulated card or a replacement driver without starting from scratch. The [86Box device](using-86box.md) was built from it. The headline finding: **Aureal's own Windows driver computes the HRTF filters and sends finished coefficients to the chip**, so an emulator needs to run fixed filters, not reproduce Aureal's 3D math.

Most of the chip's signal path is now known as arithmetic, checked against the card: the A3D engine, the crosstalk canceller, the mixer, the sample-rate converters, and the wavetable voices' interpolation, gain codes and filter. None of it is bit-exact: the chip computes in fixed point with its own rounding, which has not been recovered, and the model uses floating point. Some scales are still assumed (the wavetable pan and effect sends) and some blocks are untouched (recording, the game port, S/PDIF); the open questions at the end list them. Recordings of two period PCs with the same card playing Half-Life agree with the model's level and tone in headphone mode to about a decibel (see Comparisons with period machines).

A3D 3.0 needs nothing new from the chip: Aureal's 3.x library sends the driver the same per-source record as 2.0, and its reverb is computed by the driver on the host and returned through a capture loop (see A3D 3.0 and the driver's reverb). Reading Aureal's own debug build of the library, from the archived SDK, gave that record's layout and showed that the library's software renderer is not an HRTF renderer.

Evidence comes from one card, observed through the stock Windows 98 driver:

| Item | Detail |
| --- | --- |
| Card | Aureal SQ2500 (AU8830 "Vortex 2"), PCI revision `fa` |
| Driver | Aureal Vortex driver 4.06.2048 under Windows 98 SE |
| Host | ASUS Sabertooth X79 (BIOS 4701), card in the chipset's legacy PCI slot |
| Capture | QEMU 11.1.2 with VFIO passthrough, every register access logged; card output recorded through the host line-in |

Later sections also draw on an independent reverse engineer's register map of the chip and on descriptions from Aureal that its author relayed. They were used as leads: where the card could confirm or contradict them it was asked, and where a statement rests on them alone the text says so.

Each finding is tagged by how well it is established:

- **Confirmed**: seen directly and consistent across traces, snapshots or recorded audio.
- **Strong**: one clear line of evidence, not yet tested independently.
- **Plausible**: fits what is known, but the evidence is thin or indirect.
- **Hypothesis**: a reading that fits the data but needs a targeted test.

Register names marked "(ALSA)" come from the Linux `au88x0` driver; everything else is from our own observations. Session names (for example `20261031-142309-a3dtest2`) and "run" numbers refer to the measurement sessions listed at the end; the procedures are in [Appendix C](appendix-c-workflow.md).

## Method

The real card is handed to a Windows 98 virtual machine, and QEMU logs every read and write the stock driver makes to it, with timestamps. Nothing on the card is emulated; the driver talks to real silicon.

1. **Passthrough.** The card is bound to `vfio-pci` on the Linux host and passed to a QEMU `pc` (440FX) machine running Windows 98 SE.
2. **Trapping every access.** The device is added with `-device vfio-pci,host=…,x-no-mmap=on`. With `x-no-mmap` on, the guest cannot write to the card directly, so every BAR access goes through QEMU and is logged by the `vfio_region_read` and `vfio_region_write` trace events (`-trace … -msg timestamp=on`).
3. **Sessions.** `scripts/vortex-session.sh` starts an audio recording of the card's line-out, boots the VM with tracing on, and stores all start and stop times in UTC on the same clock QEMU uses. Trace and audio line up to well under a second; the Windows startup sound and each playback period appear in both.
4. **Register snapshots.** `vortexprobe.py snap` reads the whole 256 KB register window from the running VM through QEMU's QMP `xp` command. `vortexprobe.py cold` reads the same window from Linux after a cold boot, before any driver has touched the card.
5. **Analysis.** `vortex_trace.py` turns raw logs into a register timeline; `a3d_params.py` extracts the per-source A3D data described below.

Test content was first the A3D demos shipped with the driver package (a helicopter and a fountain moved around the listener, toward and away from them, and played as WAV sources in the player demo), then `a3dtest`, a test program in this repository that drives the A3D and DirectSound APIs one setting at a time and logs each step, and finally games (Half-Life, Unreal, Duke Nukem 3D's setup). For comparison, two period PCs with the SQ2500 (an Athlon XP and a 700 MHz Pentium III) were recorded playing Half-Life's opening tram ride, and Aureal's A3D 3.0 sample programs and two A3D 3.0 games were run in 86Box.

## PCI identity

The card is a plain PCI 2.x audio device with one 256 KB memory BAR, two 8-byte I/O BARs, no option ROM and one power-management capability (Confirmed, `lspci -xxxx` and a raw `config` read).

| Field | Offset | Value |
| --- | --- | --- |
| Vendor / device | 0x00 | `12eb` / `0002` (Aureal, Vortex 2) |
| Command / status at power-on | 0x04 | `0000` / `0290` (capability list, fast back-to-back, DEVSEL medium) |
| Revision | 0x08 | `fa` |
| Class | 0x09 | `040100` (multimedia audio) |
| Cache line / latency timer | 0x0c | `10` / `20` (host-assigned) |
| Header type | 0x0e | `00` |
| BAR0 | 0x10 | 256 KB memory, 32-bit, non-prefetchable |
| BAR1 | 0x14 | 8 bytes I/O |
| BAR2 | 0x18 | 8 bytes I/O |
| Subsystem vendor / ID | 0x2c | `12eb` / `0002` |
| Expansion ROM | 0x30 | none (`00000000`) |
| Capability pointer | 0x34 | `dc` |
| Interrupt pin | 0x3d | A |
| Min\_Gnt / Max\_Lat | 0x3e | `04` / `0c` |
| Vendor-specific | 0x40 | `80`; ALSA writes 0xff here as a PCI latency workaround for some VIA and AMD chipsets |
| Power management | 0xdc | PM version 1.0, DSI set, D2 supported, D1 not; `NoSoftRst-` |

`NoSoftRst-` means a D3 to D0 transition resets the chip's internal state. Host software that idles the card in D3, as VFIO does, therefore hands the guest a freshly reset card.

## Host interface

The chip's registers form one 32-bit address space of 256 KB, reachable two ways: directly through BAR0, or one register at a time through an index/data pair in BAR1 (Confirmed). The same register offsets are used either way.

| Path | How it works | When the Windows 98 driver uses it |
| --- | --- | --- |
| BAR0 (memory, 256 KB) | Register at offset X is BAR0 + X; 32-bit accesses | Everything once Windows is running, including all A3D traffic |
| BAR1 (I/O, 8 bytes) | Write the register offset to BAR1+0, then read or write the value at BAR1+4 (32-bit) | Early initialization only: the first \~20 s of boot, about 1,250 accesses, then never again |
| BAR2 (I/O, 8 bytes) | Byte accesses | Four accesses in a whole session: write `0x10` to +4 twice, read +6 (`0xff`), write `0x00` to +4 |

The BAR1 window matters for an emulator: the first thing the driver does is write `0x29850` to BAR1+0 and read BAR1+4 (`0x302` on this card). BAR2 is the modem side of the parallel interface, intended for the SQ3500's daughterboard: eight byte registers in a 16550 UART's layout (Plausible, register map). The driver's four accesses are a presence check: loopback on in the modem control register (+4), a read of the modem status register (+6), which reads `0xff` with nothing fitted, then loopback off. Two further details from the register map (Plausible): with the auto-increment bit of the chip control register (`0x2a00c` bit 19) set, address bits 9–2 of BAR1's address port step by one register after each data access, for the Sound Blaster TSR's reads of the FM register image; and only the wavetable block accepts byte writes, so every other register expects whole 32-bit writes. The driver sets the auto-increment bit for about 18 ms during its first initialisation, but writes the address port before every access there, so it does not depend on it; the 86Box device models it anyway.

## Address map

The chip implements registers from `0x00000` to `0x2b44f`; the remaining 80 KB of the 256 KB window is either empty or not decoded at all. Block names in the map below come from the Linux ALSA driver headers; reset contents and activity are our own observations. The map combines a cold read taken after power-on reset with snapshots of the running driver at idle, during WAV playback and during the A3D demo. The reset contents come from a read after a full power-off (power cord out). A warm reboot resets the control registers but leaves memory-like regions (route table, converter and DMA settings, filter memory) holding the previous session's values; after a true power-off those regions hold random data, and the driver initializes them itself. Control-register reset values were identical in both reads, and every register the driver reads before ever writing, and that does not change on its own, matched it (9 of 9). In the table, contents listed for memory regions (wavetable, FIFO data, A3D filter memory, mixer, converters, DMA) are as found after a warm reboot; after a power-off they are random, apart from the fixed patterns.

The last row matters for accuracy (Strong). In running snapshots, each 4 KB read chunk in this range came back as one repeated value, and each value matched a register the driver had just read, such as interrupt status `0x30024` or the counter at `0x29198`. In the cold read it looked like `0xDEADBABE` only because the last real read before it was in the `0xDEADBABE` range.

The repeated filler values (`0xDEADBABE`, `0xDEADBEEF`, `0xDEADDEAD`, `0x000DDABA`, `0x002DDEAD`) come back identically after a full power-off, while the surrounding memory is random, so they are fixed read-back values wired into the chip rather than memory contents. An emulator should return them as constants.

## AC'97 codec

**CD audio goes through the codec ADC (Strong, Half-Life sessions).** At start-up the driver mutes every analog input of the codec's output mixer (`0x10`, `0x12`, `0x14`, `0x16` = `0x8008`, CD included), sets the record select to CD on both channels (`0x1a` = `0x0101`) and the record gain to `0x0808`, and routes ADB sources `0x70`/`0x71` (the codec's ADC, left and right) to mixer inputs `0x5a`/`0x59`, which feed mixers 6 and 7 at gain `0xfa`. So CD audio is digitised by the codec and mixed by the Vortex, and the Windows CD volume acts on those mixer inputs. The real card received the same `0x12` = `0x8008` write in every traced session. The overall CD level (record gain against the drive's analog output level) has not been measured. The real card gets the same `0x1c` = `0x0808` (+12 dB) and `0x6e` = `0x0008` writes as the emulator, in every traced boot. Taking the drive's digital full scale as the codec's full scale, the Half-Life tram music came out about 14 dB above the game sound and clipped, where a recording of the game has it beneath the game sound. The datasheet's ADC −6 dB bit (`0x6c` bit 0, for CD-ROMs above 1 Vrms) is not set. Drives of the period are specified at about 0.7 Vrms line out for a full-scale 1 kHz tone into 47 kΩ, about 3 dB below the codec's 1 Vrms line-input full scale, so a full-scale CD would clip at +12 dB of record gain unless the card's CD input attenuates: the −12 dB default implies about 9 dB of attenuation in the input stage (Hypothesis). The register map's author knows of no attenuation between the CD connector and the codec on the SQ2500, and independently judged −12 dB about right, so the default stands as an empirical setting whose cause is open. The record gain reading is right: the STAC9708 manual gives `0x0` as 0 dB and `0xF` as +22.5 dB in 1.5 dB steps, so the driver's `0x0808` is +12 dB (confirmed by the map's author, correcting an earlier remark). The remaining 12 dB therefore lies in the drive's output and the card's input stage; a drive's nominal 0.7 Vrms against the codec's 1 Vrms accounts for only 3 dB. The level can be measured digitally on a real card by recording the CD through the codec (Windows Sound Recorder, record source CD) and comparing with a rip of the same track. 86Box therefore has a CD input level option, −12 dB by default (Plausible), set from the current Steam release's balance (below). Fits of a reference recording gave anywhere from −6 to −22 dB; a rough by-ear adjustment landed about 8 dB below the drive-at-full-scale level (the Windows CD slider moved the CD mixer inputs from `0x00` to `0xf5`, 8.25 dB, until the balance sounded about right against memory of the game on a real card). Not a measurement. Locating a rip of the track itself ("Black Mesa Inbound") in the recordings gives a measured balance: in a YouTube recording of the ride the music sits 13–14 dB below the game sound throughout, in both plays of the track (fit coherence up to 0.9998 in a music-only stretch, so the lossy encoding does not bias it), while in 86Box with the drive at codec full scale and the CD mixer inputs at `0x00` it sits about 5 dB above (16 windows, coherence 0.8–0.9). That is a gap of about 18 dB (interquartile 16–20) against the by-ear 8 dB. The uploader's Windows and game CD volume settings are unknown, so this is the balance of one setup, not the card's; a real-card recording of the track at known settings would settle it. A recording of the current Steam release (its own music player, not CD audio, so Valve's present-day balance rather than the card's) puts the music about 7 dB below the game sound (median of 20 windows, interquartile −9 to −4 dB): a 13 dB gap from 86Box at 0 dB, which the default follows. **A real card agrees with the default (Strong, Pentium III capture of 2026-11-15).** A 700 MHz Pentium III with the SQ2500, recorded playing the same ride with the disc in the drive and Windows' mixer at its untouched settings, put the music about 4 dB lower against the game sound than an 86Box run at the −12 dB default (±3 dB: the two runs do not play out identically). Setting the 86Box guest's sliders to match a photograph of the Pentium III's moved the CD mixer inputs from −7.8 to −11.0 dB, with Wave Out at −4.1 dB, a 3.2 dB change that accounts for the gap. At matched settings, then, the default reproduces the card's balance within the measurement's uncertainty; the cause of the 12 dB (drive output, card input stage) is still not known.

The SQ2500's analog side is a SigmaTel STAC9708/9711, AC'97 vendor ID `0x83847608` (Confirmed: read by the driver from codec registers `0x7c` = `0x8384` and `0x7e` = `0x7608`).

The driver reaches the codec through `CODEC_IO` at `0x29188` (ALSA):

| Bits | Meaning |
| --- | --- |
| 23 | 1 = write, 0 = read request |
| 22–16 | AC'97 register number |
| 15–0 | Data |

A read is a write of the register number with bit 23 clear, followed by a read of `0x29188`; the returned word repeats the register number in bits 22–16 with the data below.

**Vendor register `0x72` selects the driver's rear-inversion workaround (Strong).** The real codec returns `0x8000` from `0x72`, and the driver then reads `0x6e` and writes `0x0008` to it. A codec that returns 0 there (86Box before its fix) sends the driver down another path: it writes `0x0007` to `0x72`, never touches `0x6e`, and loads the Vortex EQ with every band's numerator and the bypass gain negated (bypass `0x8001` instead of `0x7fff`). Only the front path runs through the EQ, so the chip's rear outputs then carry the exact negative of the front. The registry names the setting `ST9708LA4RearInversion` (`HKLM\Software\Aureal\Vortex\AU8830\Customization`, 1 by default): presumably a STAC9708 revision whose rear DAC inverts, which bit 15 of `0x72` tells apart. The EQ coefficients themselves come from the registry (`…\AU8830\Equalizer`, `CoefSet0`, with the real card's signs), so the negation is the driver's own.

Startup sequence, in order:

1. Write register `0x00` (reset); read the vendor ID at `0x7c` and `0x7e`.
2. Write SigmaTel-specific registers: `0x76` = `0xabba`, `0x78` = `0x1000`, `0x70` = `0xabba`, `0x72` = `0x0007`. (`0xabba` looks like an unlock value for SigmaTel's extended registers; Hypothesis.)
3. Read extended audio ID `0x28` (`0x0080`) and status `0x2a` (`0x0080`); read powerdown status `0x26` (`0x000f`) and set it to `0x800f`.
4. Set mixer levels, then fade the master volume (`0x02`) from `0x3f3f` to `0x0808` in 56 steps of about 0.12 ms each.

Full per-register tables are produced by `vortexprobe.py codec` from any boot trace.

## A3D engine

Each positioned sound is a source holding a 56-tap FIR filter per ear, an interaural time delay (ITD), a gain and an "atmospheric" filter. The driver computes all of them on the host and writes them as **targets**; the chip keeps its own **current** values and glides them toward the targets, so parameter changes don't click. Direction lives in the FIR taps and the ITD; distance and occlusion live in the gain and atmospheric filter. The register names come from ALSA's `au88x0_a3d.h`; the behavior described here is what the traces and recordings show.

### Memory layout

There are 16 source slots: four 8 KB slices, each with four sources. This matches the `NR_A3D 0x10` constant in ALSA's `au8830.h`.

| Offset from source base (bank B) | ALSA name | Observed |
| --- | --- | --- |
| `+0x000`, 56 words | `HrtfCurrent` | Written when a sound starts; otherwise maintained by the chip |
| `+0x0e0` / `+0x0e4` | `GainCurrent` / `GainTarget` | Target rewritten during play; this is the distance and occlusion gain |
| `+0x0e8` / `+0x0ec` | `A12Current` / `A21Target` | Atmospheric filter feedback coefficients (two 16-bit values) |
| `+0x0f0` / `+0x0f4` | `B01Current` / `B10Target` | Atmospheric filter feedforward coefficients (two 16-bit values) |
| `+0x0f8` / `+0x0fc` | `B2Current` / `B2Target` | Always 0 in our traces |
| `+0x100`, 56 words | `HrtfTarget` | Rewritten continuously during play |
| `+0x1e0` / `+0x1e4` | `ITDCurrent` / `ITDTarget` | Target rewritten when the direction changes. Lower half = left-ear delay, upper half = right-ear delay; only the far ear is nonzero. `0x200` = one 48 kHz sample, up to about `0x5000` |
| `+0x1e8`, 56 words | `HrtfDelayLine` | Filter state; written at startup |

The source base is `0x19000 + slice × 0x2000 + source × 0x2c8` (ALSA `a3d_addrB`). Example: slice 3, source 2 is `0x1f590`, so its filter target is `0x1f690`. A second per-source bank, `0x18000 + slice × 0x2000 + source × 0x3a4` (`a3d_addrA`), holds the same names plus the ITD delay line (`+0x2c8`, the 45-word blocks written at startup), tracking time constants (`+0x37c–+0x388`) and filter state. Our traces show the driver using bank B during play. Each slice also has control registers at `0x19c00–0x19c40 plus slice × 0x2000` (`VDBDest`, `VDBSource`, `ABReg`, `CReg`, `Control`, `DebugReserved`, `Pointers`); `DebugReserved` (`0x19c3c` in each slice) is the one word the driver changed there between reset and idle.

Slot allocation (Confirmed, test-suite run 2): the driver hands out slots from 14 downward. The first 3D sound goes to slot 14 (slice 3, source 2), the next to 13, and so on down to 0, and slots are freed in reverse. With 16 sounds requested, only 15 slots were ever used; slot 15 was never given to a source.

At reset the implemented words are zero and the gaps between them read `0xDEADBABE` (see Address map).

### Filter coefficients

Each of the 56 words packs two signed 16-bit taps: **upper half = right ear, lower half = left ear** (Confirmed). With the recorded output lined up against the trace, the left/right level difference of the audio follows the coefficient balance (correlation −0.81); when the upper half carries more energy, the right channel is louder.

- The taps decay from the start of the block, the usual shape of a head-related impulse response.
- The louder (near) ear peaks at tap 0; the quieter (far) ear peaks 3 to 8 taps later. The main interaural delay is carried separately by `ITDTarget` (Confirmed): the lower half delays the left ear and the upper half the right ear, and `0x200` is one sample at 48 kHz (a 16-bit delay with 9 fractional bits). The driver's values follow a spherical-head (Woodworth) curve: 7 samples at 15°, 19 at 45°, 35 at 90°, and a maximum of 37–38 samples (about 0.78 ms) just behind the side. Elevation shrinks it (at 90° azimuth: 22 samples at 45° up, 0 straight up). Exactly 180° is a special case in the driver (see the direction table below). In the recording, the interaural lag matched the register to within about a sample wherever the click cross-correlation was clean (15°, 180°, 195°, 210° and 330°).
- As a sound circles the listener, the energy balance between the halves swings smoothly between about +15 dB and −16 dB.
- Total coefficient energy does not change with distance; distance is handled by the gain and atmospheric filter.
- Updates arrive roughly 8 to 20 times per second per source, depending on the program.

Tap scaling (Strong): the taps behave as Q15 at the same overall level as a plain (non-3D) source. Clicks recorded at 44 positions were compared with the clicks predicted from the register taps, ITD and gain. Once the speaker crosstalk below is accounted for, the recording matches the prediction to 4–10% residual below 2.4 kHz. The fitted overall scale of the 3D path (−3.7 to −9.2 dB across octave bands, average about −6.5 dB) agrees within about 2 dB with a native click through the same recording chain (−7.3 dB). The left and right tables are separate measurements, not mirror images: at 90° the near-ear taps correlate 0.87 with the mirrored 270° near-ear taps. The exactly-180° result is a separate case, described with the direction table.

### The arithmetic, read on the card (Confirmed, `a3dprobe`, 2026-11-17)

With the card idle under Linux, one source (slot 0) was set up as the driver's pass-through (one tap of `0x7fff` at index 0, gain `0x7fff`, b0 `0x4000`, tracking off), fed from an ADB FIFO, and each output of its slice read digitally through a converter at ratio 1; then one field was changed at a time (61 cases, both ears). Data: `data/a3dprobe-20261117.jsonl`, `.npz`.

- **The slice's outputs are halved.** Any input x came back as x/2 rounded toward zero, from full scale down to the last bit (1 → 0, 2 → 1, 3 → 1, −1 → 0, −3 → −1, 8,192 → 4,096, 32,767 → 16,383, −32,768 → −16,383). With b0 at `0x7fff` (2.0) a full-scale input read 16,383, so the output saturates at 16 bits first and is then shifted. This is the one-bit shift on the A3D outputs that the map's author gives.
- **Word formats.** Taps and gain are Q15 (`0x4000`, `0x2000`, `0x1000`, `0x0800` give ½, ¼, ⅛, 1/16; `0x8000` is −1; `0xc000` −½). The atmospheric filter's coefficients are Q14: b0 `0x2000`, `0x4000`, `0x7fff` give 0.5, 1 and 2, b1 adds to b0, and a1 `0x2000` makes a pole at 0.5 (impulse 8,192, 4,096, 2,048, …; step rising 2,048, 3,072, 3,584, … to 4,096), feedback with a plus sign. Two taps of `0x7fff` summing past full scale clip like a single overload.
- **Taps and delay.** A tap's index is its delay in samples (taps at 0 and 3 gave impulses 3 samples apart; tap 55 the latest). The ITD is in 1/512 sample with linear interpolation: `0x100` split an impulse 4,096 / 4,096, `0x80` 6,144 / 2,048, `0x600` and `0x1000` delayed it 3 and 8 samples, each ear by its own half.
- **Ears.** In the targets the low half is the left ear; in the currents (which the chip uses) the high half is. Swapping the currents' halves swapped the ears.
- **Readback.** The A3D sources' words take 32-bit writes but read back their low 16 bits only (`GainCurrent` written `0x7fff7fff` reads `0x7fff`, `B01Current` `0x40000000` reads 0, a tap pair `0x467c39a1` reads `0x39a1`; `pathprobe` run 3). The Windows driver never reads them. The model returns the whole word.
- **The distance filter's words (`a3dprobe atmos`).** In the currents, `A12Current` holds a1 in the high half and a2 in the low half (a2 `0x2000` alone gave 8,192, 4,096 … every other sample; `−0x2000` the same alternating in sign; a1 `0x4000` with a2 `−0x2000` the expected pair of complex poles), `B01Current` b0 high and b1 low, `B2Current` b2 high (the low half did nothing). The driver's own set (b0 `0x00fe`, a1 `0x700a`, a2 `0xcef7`) written this way is a stable low-pass rising to the input's level. All as the model reads them. With the driver's tracking rates the currents had not moved toward new targets within the 3 ms of a capture. Data: `data/a3dprobe-atmos-20261117.jsonl`, `.npz`.

**The whole 3D path against the native one (Confirmed, `pathprobe` run 4, 2026-11-17).** With every register the driver had set in test-suite run 4 at 125 s (a front 3D click at gain 1.0, headphone mode) loaded on the idle card, a constant of 8,192 came out of mixer 0 at 4,096 through the native path (mixer 4 at `0x08`, mixer 6 at `0x00` = ½, the EQ at its pass-through, mixer 0 at `0x08`) and at 2,663 through the 3D path. The 3D path's stages read 2,273 at the slice (8,192 × ½ for the shift × 0.556 for the left ear's taps × 0.996 for the distance filter), 2,841 at the canceller (× 1.25 for headphones) and 2,663 at mixer 0 (× 0.9375 for the driver's `0x07`): the arithmetic above to within 0.2%, with no further factor anywhere. The factor of 0.75 that the model carried came from a hand calculation in the crosstalk work that took the canceller's mixer input as `0x0a` (× 1.25) and the native path as unity; in every traced test-suite run the driver set `0x07`, and the native path runs through mixer 6 at ½. With that factor the model played 3D sound 3.5 dB too loud against everything else; it has been removed (86Box, 2026-11-17). Data: `data/pathprobe-20261117-4.jsonl`, `.npz`.

The current-versus-target behavior is visible on real hardware. In a running snapshot during A3D, the card read back gain `0x4183` while the driver's last target was `0x4234`, and the filter coefficients sat similarly between old and new targets. The glide is done by the chip (Confirmed): for an abrupt change the driver writes the new target once and never touches the current value. Measured from the recordings of both test-suite runs:

| --- | --- | --- | --- |

| Atmospheric filter coefficients | `CoeffTrackTC`, `0x300` | Exponential glide of the coefficients themselves, 50–62 ms. This reproduces the lopsided response: switching the filter in takes about 400 ms to sound finished, switching it out about 100 ms | Confirmed |
| HRTF taps | `HrtfTrackTC`, `0x147` | About 115–130 ms | Confirmed |
| ITD | `ITDTrackTC`, `0xc8` | About 80–90 ms | Confirmed |

The four time-constant words sit in bank A at +0x37c (`HrtfTrackTC`), +0x380 (`GainTrackTC`), +0x384 (`CoeffTrackTC`) and +0x388 (`ITDTrackTC`). The driver writes `0x147`, `0x300`, `0x300` and `0xc8` when a source starts and 0 when it stops; these are also ALSA's defaults. Run 4 rewrote each word from the host while a source played (headphone mode, two 9-second cycles per value) and measured the glides from the recording (Confirmed):

| --- | --- | --- | --- |

| `CoeffTrackTC` | `0x100`, `0x180`, `0x300`, `0x600`, `0xc00` | 182, 116, 57–62, 33, 19 ms | 171, 114, 57, 28, 14 ms |

| `ITDTrackTC` | `0x32`, `0xc8`, `0x320`, `0xc00` | 220, 82–86, 35, under 21 ms | 874, 218, 55, 14 ms |

Each word controls only its own value: changing one left the other three glides unchanged. The audio measurements above were coarse; reading the current registers back directly settles the law (Confirmed, glidewatch session 2026-11-01, which polled the currents every 100 µs after each target change). The chip updates the currents once every **64 samples** (1.33 ms at 48 kHz), not every sample. Each update moves the value **TC × 64 / 2²¹** of the remaining distance for gain, filter coefficients and HRTF taps, and **TC × 64 / 2¹⁹** for the ITD. That makes the time constants 2²¹ / TC samples (gain, filter, HRTF) and 2¹⁹ / TC samples (ITD); the ITD is four times faster than the others at the same TC. Fitted τ × TC came out at 2.00–2.07 million for gain, filter and HRTF (2²¹ ≈ 2.10 million) and 0.49–0.52 million for the ITD (2¹⁹ ≈ 0.52 million), and at gain TC `0xc00` each update leaves exactly 0.90625 of the remaining distance (1 − 3072 × 64 / 2²¹). At the driver's defaults the glides are about 130 ms for the HRTF (`0x147`), 57 ms for gain and filter (`0x300`) and 55 ms for the ITD (`0xc8`). An emulator should step the values every 64 samples by these fractions. Aureal's description, relayed by the map's author, gives the rule behind the numbers: each TC word is a tracking rate T in 1.15 fixed point (0 = off, just under 1 = fastest), each update moves a value T of the way to its target, gain, filter and HRTF values are updated once every 64 samples, and the delay once every 16. T × 64 / 2²¹ is T / 32768, and four updates of T / 32768 in the time of one are the measured T × 64 / 2¹⁹ for the ITD. The emulator uses the rule (the four delay updates applied together at each 64-sample step). The register map accounts for the 64: the A3D control word (`0x19c38` and its siblings) has a 6-bit counter in bits 8–13 that selects which coefficient is smoothed in the current sample period. So the chip moves one coefficient per sample and gets round to each once every 64 samples; the values are probably updated on different samples of the cycle, not all together as the emulator does (Plausible).

**Occlusion** (A3D Rooms demo) appears as simultaneous jumps in all three targets. Example, one source:

**The atmospheric filter is a two-pole low-pass with unity DC gain, in Q14 fixed point** (Confirmed). Reading the words as signed 16-bit values divided by 16,384:

- `A21Target` upper half = a2, lower half = a1; `B10Target` lower half = b0, upper half = b1 (always 0 so far); `B2Target` = b2 (always 0).
- The filter is y\[n\] = b0·x\[n\] + b1·x\[n−1\] + b2·x\[n−2\] + a1·y\[n−1\] + a2·y\[n−2\].
- Check: (b0 + b1 + b2) / (1 − a1 − a2) = 1.000 at the median of all 1,823 updates in the Rooms, distance and Helicopter traces (5th–95th percentile 0.994–1.000), and every pole lies inside the unit circle.
- Nearest setting: a1 = a2 = 0, b0 = `0x4000` = 1.0, a straight pass-through. Farthest helicopter setting: a1 = 0.896, a2 = −0.200, b0 = 0.305. Occluded Rooms source: a1 = 1.806, a2 = −0.815, b0 = 0.0095, a much darker double pole near 0.90.

So distance and occlusion both work by sliding this low-pass's cutoff down while the gain target drops. `GainTarget` is Q15 (`0x7fff` = 1.0), and the filter is always a double real pole; both are confirmed by the test suite below.

### The driver's direction table (Confirmed)

Test-suite run 2 stepped one source through every 5° of azimuth at elevations −45° to +90° in 15° steps (649 positions, plus 1° steps from 170° to 190°) and recorded the taps and ITD the driver wrote for each. All 24 positions also measured in run 1 match exactly.

- The driver's table has an entry every 15° of azimuth. Positions in between are a straight linear interpolation of the two neighbouring entries, taps and ITD alike (second differences are 1–3 units, rounding).
- That gives 217 grid entries over the measured range (24 azimuths × 9 elevations from −45° to +75°, plus straight up). Each entry is 56 left and 56 right taps and a two-ear ITD.
- The ITD is fractional: 5° at −45° elevation gives `0x354` (1.66 samples), exactly a third of the 15° entry.
- **Exactly 180° is a special case, not the table's 180° entry (Confirmed).** A source placed exactly behind gets taps 3–9 times the amplitude of its neighbours and a large one-ear ITD (40 samples on the left ear from −15° to +30°, 16 at ±30–45°, 0 at −45° and above 45°), the same in every run. But it is not what the driver interpolates with: 179° and 181° (1° sweep at 0°), and 175° and 185° at every elevation, are linear blends of 165°/195° with a normal-looking 180° entry that has zero ITD and ordinary energy. The 180° entry reconstructed from the 165–180 side and from the 180–195 side agrees to 0.1% at every elevation. So the table's real 180° entry is ordinary, and an exactly-180° direction takes a different path in the driver (Hypothesis: the ±180° boundary of the angle calculation sending the lookup outside the table). Games would only hit it with a source exactly behind the listener. An emulator gets this from the driver either way; a renderer using the table should use the reconstructed entry.

Run 3-2 stepped elevation in 5° steps at four azimuths: the elevation grid is also 15°, with the same linear interpolation. Run 12 moved a source over a 3.75° grid in three regions (351 positions) and confirmed that the driver interpolates bilinearly in azimuth and elevation together: every position matched bilinear interpolation of the table to within rounding (0.05%), against 7–16% for nearest-point or one-axis schemes. [Appendix A](appendix-a-direction-table.md) describes the table and how it was read out of the driver with a card; the table itself is in `data/hrtf/`. A driver-replacing wrapper needs it; an emulator running Aureal's driver gets it from the driver.

### Reflections, stereo mode and speaker output

**Reflections do not use extra A3D sources.** The Helicopter demo used a single source with Reflections on or off. Reflections instead show up in wavetable voice 0's parameter registers. This fits a developer's account on VOGONS that A3D 2.0 WaveTracing is computed in `A3DAPI.dll` and the results are sent to the wavetable engine.

| Register (ALSA WT name) | Reflections on | Reflections off |
| --- | --- | --- |
| `0x200` / `0x204` (`PARM0` / `PARM1`), upper half | `0xcca6–0xccb2`, rising and falling with the helicopter's orbit (about 10 s per cycle) | Fixed `0x8400` |
| `0x20c` (`PARM3`) | Varies, `0xcfefd8ff–0xcfefffff` | Fixed `0xcfefffff` |

The reflection delay setting has not been located. The WT delay registers (`0x400–0x40c`) stay 0. Moving the slider produced step changes only in FIFO control (`0x16000`, `0x16100`) and the DMA start registers (`0x27b00`, `0x27c00`), which looks like the demo restarting its sound buffers; that fits the reflection delay being applied by timing rather than by a register (see below). One run with the slider at an extreme left reflections in their off state throughout. In the test suite (a reflective wall 2 m to the side), changing the delay scale or the maximum delay time changed no register value either. The gain scale did: bits 16–23 of `PARM0`/`PARM1` went `0xa0` → `0x90` for ×0.5 and `0xb0` for ×2, so that byte is a logarithmic gain with `0x10` per 6 dB (Strong). Setting the wall's reflectance to 0.5 (low) / 0.1 (high) gave `0xa090a000` instead of `0xc6a0a000`: the gain byte dropped 6 dB and the top byte changed from `0xc6` to `0xa0`, so the top byte probably carries the high-frequency (filter) part (Hypothesis).

The recording settles the delay question (Confirmed). In the test suite the source was 4 m ahead with a wall 2 m to the right, so the reflected path is 1.66 m longer, or 4.8 ms at 343 m/s. An echo appears about 4 ms after each click when the wall is present and not without it. It moves to about 2, 9 and 19 ms for delay scales 0.5, 2 and 4, and its level changes by about −7 and +6 dB for gain scales 0.5 and 2. No chip register changed with the delay scale, while the wavetable DMA page pointers (`0x27000–0x2700c`, with `0x27600`/`0x27604`) cycle continuously. The reflection signal is therefore computed on the host, delay included, and streamed to the card through a wavetable DMA channel; the chip only plays it at the gain set in `PARM0`/`PARM1`.

Run 2 mapped the reflection voice's `PARM0`/`PARM1` fields (Strong). The two words differ only in the lowest bit (`0x…a000` and `0x…a001`), which looks like a left/right voice pair.

| Change (wall 2 m right unless noted) | `PARM0` | Echo in recording |
| --- | --- | --- |
| Reflectance 1.0 / 1.0 | `0xc6a0a000` | 4 ms, −10 dB |
| Low reflectance 0.5, 0.25 | `0xc690…`, `0xc680…` | −14, −21 dB |
| High reflectance 0.5, 0.25, 0.1 | `0xb0a0…`, `0xa7a0…`, `0xa0a0…` | −16, −17, −21 dB (duller) |
| Wall at 1 m, 4 m, 8 m | `0xc8a6…`, `0xc293…`, `0xba83…` | 4 m: about 14 ms (predicted 14.4) |

Bits 16–23 are the reflection gain in steps of 6.02/16 = 0.376 dB, and they include the longer path. Bits 24–31 follow the high-frequency reflectance and the distance, and they set a low-pass filter (see run 14 below). With two or three walls the driver still used only this one voice pair, so additional reflections are mixed on the host into the same stream.

**Test-suite run 14 (`run13`, wall 4 m to the right, echo 13–15 ms after each click) measured both bytes against the recorded echo (Confirmed).**

- **Gain byte.** Lowering the wall's low-frequency reflectance dropped the gain byte from `0x93` to `0x8c`, `0x83`, `0x7a`, `0x73` and `0x5e` for reflectance 0.75, 0.5, 0.35, 0.25 and 0.1. The echo fell by the same amount at every frequency: 3.6, 7.0, 9.2, 12.5 and about 19 dB. So low-frequency reflectance is pure gain, at `0x10` per 6 dB, and reaches the chip only through this byte.
- **Top byte.** Lowering the high-frequency reflectance changed only the top byte: 1.0, 0.75, 0.5, 0.35, 0.25, 0.15, 0.1, 0.05 and 0 gave `0xc2`, `0xb6`, `0xac`, `0xa7`, `0xa4`, `0xa1`, `0x9d`, `0x95` and `0x84`. Dividing each step's echo spectrum by the full-reflectance step's (1/3-octave bands, 300 Hz to 10 kHz, only where at least 6 dB above the noise) cancels the head-related and recording responses. What is left fits a two-pole low-pass with Q ≈ 0.64 (0.7 dB rms), better than one, two or three cascaded one-pole sections (1.8, 1.0 and 0.8 dB, with worse residual shapes). The fitted cut-offs were 4.7 kHz, 2.1 kHz, 1.2 kHz, 920, 800, 640, 570, 455 and 250 Hz. They follow log2(fc) = 13.505 + 1.817u + 0.139u², with u = (byte − `0xcf`) / 16, to within 0.8 dB rms. That law puts `0xcf` at about 11.6 kHz. Since the driver uses `0xcf` for voices that must pass unchanged, `0xcf` and above are taken as no filter (Strong). Aureal's description calls the wavetable filter a second-order Butterworth low-pass (Q 0.707), and its product brief speaks of "sweepable filters with resonance"; the measured Q of about 0.64 is close to Butterworth, and resonance control, if any, has not been located.
- **Echo level.** Below about 500 Hz, where neither the filter nor the crosstalk canceller (next point) does much, the echo's level relative to the direct click matched the emulator within about 1 dB. So the reflection gain needs no correction.
- **Crosstalk canceller.** The X79 machine's driver stayed in satellite-speaker mode throughout runs 2, 13 and 14 (`0x24660` = `0xc085ad89`, delay 13), even though A3DTEST asked for headphones and the call succeeded. So on the real card, the direct (A3D) sound in these recordings went through the canceller, which adds about 8 dB around 1–1.5 kHz, while the echo (wavetable voice → mixer) did not. Comparisons of echo against direct sound with the emulator need the same speaker setting on both.

**Stereo mode** (Helicopter's "Audio: Stereo") leaves the A3D sources idle. Mixer input volumes ramp continuously instead: current values at `0x202xx`, targets at `0x212xx`. That is ordinary panning through the mixer, again with current/target pairs.

Plain (non-3D) playback is a clean unity path (Confirmed, run 2): a 48 kHz click in only the left or only the right channel comes out of that channel at the same level as the recording chain's own gain (−7.2 dB, flat from 150 Hz to 10 kHz), with the other channel more than 45 dB down. A mono or stereo-both click reaches the left output after the right, by 8–9 samples in run 1 and about 15 samples in run 2. The 3D path shows no such offset. Whether this comes from the native routing or the codec is still open.

**Speaker crosstalk cancellation** lives at `0x24000–0x25fff` (ALSA au88x0\_xtalk.c), the block that changes only once A3D starts. Run 1 of the test suite (default output mode, which is a speaker mode) shows it working (Confirmed). Each output channel equals that ear's FIR result plus X(f) times the other ear's, with the same X for both channels. Fitted over 44 click positions, |X| is about 1.0 at 150–300 Hz, 0.9 at 300–600 Hz, 0.64 at 0.6–1.2 kHz, 0.46 at 1.2–2.4 kHz and about 0.25 above that. Its phase is close to an inversion delayed by about 0.4 ms. In other words, it is a classic canceller: the far channel gets an inverted, delayed, low-passed copy of the near channel. Adding it cuts the model error from 40–80% to 4–10% below 2.4 kHz. It explains why the recorded left/right swing is much smaller than the filter balance. The A3D API's `SetOutputMode` does not change it (Confirmed, run 2). Headphones, wide speakers and narrow speakers gave the same X to two decimal places, and no register in `0x24000–0x25fff` changed; narrow speakers returned E\_INVALIDARG. The mode is presumably taken from Aureal's control panel, so measuring the canceller off, and its coefficients per mode, needs the panel setting changed between runs.

ALSA's code gives the register layout: for each ear an EQ filter and a crosstalk (XT) filter of five 5-word sections each (`0x24200`, `0x242b4`, `0x24368`, `0x2441c`, each + section × 0x24), gains and shifts at `0x24538–0x24554`, and the delay at `0x24660`. It does not give the arithmetic.

**Structure (Confirmed, runs 9 and 10, host writes).** Each side has an EQ stage, and the crosstalk is mixed from the other side's EQ output. Zeroing both EQ gain words changes the left and right outputs by the same complex factor, and raising the left EQ's shift raises both outputs. ALSA's "XT left" filter feeds the right output and "XT right" the left. With every gain word at 0 the canceller passes sound straight through, which is what headphone mode does; the filter sections are then irrelevant.

**Arithmetic (Confirmed).** Each of the four blocks (EQ and XT per side) computes 2^shift × (k × input + the sum of its five sections, all fed the input); the sections are ordinary second-order sections with 2.14 coefficients, in parallel. Each output is its own side's EQ block plus the other side's EQ output, delayed by the control word's delay and passed through that side's XT block. The headphone preset is the same arithmetic with flat sections and no XT. With the driver's presets this reproduces the measured responses of both speaker settings relative to headphones to 0.2–0.6 dB, level and delay included, with nothing fitted; [Appendix B](appendix-b-crosstalk-model.md) has the evidence and the arithmetic in full. The gain word k is the block's direct path, not a gain on the sections, which is why the earlier sweeps did not make sense of it.

**Which preset is loaded (Confirmed, 2026-11-15 sessions).** Only the control panel's speaker setting changes the canceller. `IA3d4::SetOutputMode` from a program does not: asking for headphones or wide speakers returns success and leaves the registers alone, and asking for narrow speakers returns `E_INVALIDARG`. With the panel on satellites the satellites preset stayed loaded through a test's "headphones" steps, and likewise for monitors. So the mode names in `a3dtest`'s `xtalk` and `ref` logs describe the request, not the canceller; the earlier runs that compared modes did so by changing the panel between sessions. The driver also reloads the whole preset (through a brief all-zero state) each time a source starts.

**The arithmetic, read on the card (Confirmed, `xtprobe` run 1, 2026-11-17).** A constant or an impulse from an ADB FIFO into one canceller input, each output read digitally through a converter (data: `data/xtprobe-20261117-1.jsonl`, `.npz`):

- **Direct path.** Input gains (`0x244d0` + input × 4) are Q15 (`0x3fff`/`0x4000` ½, `0x2000` ¼, `0x8000` −1); k is Q14 (`0x2000` ½, `0x4000` 1, `0x7fff` ≈ 2, `0x8000` −2); the shift multiplies by 2^shift (k `0x0800` with shifts 1–4 gave 2,048, 4,096, 8,192, 16,384 for 8,192 in); the output saturates at 16 bits. Inputs 0–4 reach the left side and 5–9 the right.
- **Sections.** Of a section's nine words, 0–4 are a1, a2, b0, b1, b2 (Q14; a1 `0x2000` with b0 `0x4000` gave 16,384, 8,192, 4,096 …, a2 the same every other sample, b1 and b2 a copy one and two samples later); 5–8 had no effect when written, presumably the section's state. Sections add to each other and to the k path. This is the order the model uses.
- **Headphones.** With the driver's headphone preset the card gave 1.2499 × the input (8,192 → 10,239) through an input with gain `0x3fff`: five flat sections summing to 1.25, shift 1, gain ½, exactly the model's arithmetic. So the 3D path's remaining factor of 1.5 is not in the canceller.
- **Held inputs.** A canceller input keeps the last sample routed to it: the preset cases, with eight input gains on, also read the constants that earlier cases had left on other inputs (one input's worth on the right, two on the left, the same at every sample). That also confounded this run's input-mapping cases and filled the two speaker presets to clipping; run 2 zeroes all ten inputs before each capture.
- **Rounding.** The gain product rounds to nearest with the input carried at a few extra bits, and so does the k product (0x3fff on 1, 3, 5, 7 gave 1, 2, 3, 4; on −1 and −3, 0 and −1; 0x7fff on 32,767 gave 32,766). One case (k `0x0001` on 8,192, 0.49998 → 1) does not fit that yet.

**Run 2 (Confirmed, 2026-11-17).** With all ten inputs zeroed before each capture: inputs 0–4 feed the left side and 5–9 the right, each scaled by its own gain word only; an input left unfed holds its last sample (4,096 fed to input 0 after 8,192 on input 1, both gains on, read 12,288); the "XT left" block feeds the right output and "XT right" the left. The satellite and monitor presets, impulse in, matched the model's arithmetic to 1 LSB over 110 samples on both outputs (one capture had a single glitched sample), as did headphones. So the canceller reproduces the card's digital output; the 2–3 dB bass and treble differences against the period-machine recordings in the speaker modes are not in its arithmetic. The delay word was not checked digitally (left and right came from separate captures, and fanning one FIFO to two inputs fed only the first), but the analog runs had confirmed it. Data: `data/xtprobe-20261117-2.jsonl`, `.npz`.

**Cross-feed delay (Confirmed, `restprobe xtdelay`, 2026-11-17).** Two VDB FIFOs started together (checked: impulses placed 4 samples apart came out 4 apart) fed inputs 0 and 5, so the direct and the cross-fed impulse land in one capture. Written in the driver's satellite-mode sequence (`0xa0000000` + delays, then `0xd0000088` and `0xc0000089` + delays), the left field (bits 17–13) delayed the cross copy on the right output by exactly its value in samples (1, 5, 13 and 31 gave gaps of 1, 5, 13 and 31) and the right field (bits 12–8) did the same on the left output (7 and 13), as the model has it. Written in the headphone-mode sequence (`0xa0000000`, then `0xc0840088` and `0xd0840089` + delays), no delay took effect at any setting. In every traced sequence the delays are carried by the write whose top nibble is `0xa` (`0xa001ad00` for satellites, `0xa000e700` for monitors, `0xa0000000` for headphones), so the likely reading is that bit 29 enables writing the delay field and the later writes leave it alone; the model, which takes the delay from the last write, gives the same result for every sequence the driver uses. Data: `data/restprobe-20261117-1.jsonl`, `data/restprobe-20261117-2.jsonl`.

**Control word (host readback).** Bits 17–0 of `0x24660` read back as written (`0x1ad89` for satellites). The bits above them change from read to read; they are live state of the block, not settings.

**Model.** The 86Box device and `data/xtalk/vortex_xtalk.py` run this arithmetic on the live register contents (in floating point; the chip's fixed-point rounding is not reproduced). It adds no latency. The measured 512-tap filters used before are superseded, along with a 5.5–6.2 dB level reduction that turned out to be wrong (Appendix B).

**Four-speaker output (Confirmed, runs 6 and 7).** The rear jack is always live. The route list sends mixer outputs 0/1 to codec slots 0/1 (front) and mixer outputs 2/3 to codec slots 4/5 (rear) in both stereo and quad mode. What changes is the mixer:

- **Stereo:** the rear mix is a copy of the front mix (the 2D sound and the crosstalk canceller's output, at the same gains).
- **Quad:** the 2D mix goes to all four outputs at −3.8 dB. The A3D/canceller output goes to the front only. The rear instead gets a plain copy of each 3D source, without HRTF processing, through its own mixer input (input 26 in this run, fed by a wavetable channel), panned left/right by the driver. The driver also turns the source's front `GainTarget` down as it moves behind the listener.

| Azimuth | Front 3D gain | Rear left | Rear right |
| --- | --- | --- | --- |
| 0°, 30° | 0 dB | off | off |
| 60° | −0.2 dB | off | −19.5 dB |
| 90° | −1.8 dB | off | −10.5 dB |
| 135° | −10.2 dB | off | −6.0 dB |
| 180° | off | −3.8 dB | −7.5 dB |
| 270° | −1.8 dB | −10.5 dB | off |

**The model reproduces it (Strong, replay of run 6).** Replaying run 6's register trace into the model with four-channel output (`v2replay -q`) gives, after removing the noise the replay feeds into the test's silent 2D buffer (which lands equally on all four outputs, as the 2D path should), rear levels relative to the dry source of −19.9 dB (60°, right), −10.7 dB (90°, right), −6.0 dB (135°, right), −3.7 and −7.5 dB (180°, left and right) and −10.4 dB (270°, left), with the opposite rear channel off: all within 0.4 dB of the table. The model's front output follows the real front-jack recording across the steps (no change from 0° to 90° within 0.5 dB, about 15 dB down at 135° against 14 dB on the card, off at 180°).

So quad mode is a front/rear crossfade done by the driver with ordinary mixer gains; the chip needs no extra 3D hardware for it. In quad mode the driver gave out only 11 hardware 3D slots (14 down to 4) instead of 15. In run 6 the speaker type was satellites; the rear did not get its own canceller.

**The EQ block (Confirmed, run 9, host writes).** The chip's EQ at `0x2b000` sits in the 2D path: mixer outputs 6/7 → EQ → mixer inputs 7/8 → front and rear outputs. The Windows driver leaves it transparent: every band gain is 0 and the bypass gain (`0x2b3d4` left, `0x2b3ec` right) is `0x7fff`. Switching it on from the host showed:

- Output = bypass gain × input + the sum of ten band-pass filters, each times its band gain (`0x2b02c` + band × 0x30 left, `0x2b20c` + band × 0x30 right). Bypass 0 with every band at 0 silences the 2D mix (about 50 dB down). Bypass `0x3fff` gives −6 dB, so the bypass gain is linear Q15.
- The bands are octaves centred on 31, 63, 125, 250, 500 Hz, 1, 2, 4, 8 and 16 kHz. Each is a band-pass about 6 dB per octave down on either side of its peak.
- ALSA's "normal" band gain `0x3e96` gives unity at the band centre, and all ten at `0x3e96` with bypass 0 sum to flat within about 1 dB.

- **The bypass and band gains are signed and simply add (Confirmed, run 16).** With band 4 (500 Hz) at `0x3e96` the 500 Hz region rose 5.0 dB with the bypass at `0x7fff` and fell 11.7 dB (a notch) with the bypass at `0x8001`; the bypass at `0x8001` alone changed nothing audible (a polarity flip); band 4 alone gave a band-pass, −2.1 dB at its centre and −15 to −28 dB well away from it. The emulator's EQ, driven by the band-4 coefficients from the driver's registry set, reproduces all four within 0.4 dB.
- **Gain tracking (Plausible, Aureal's description).** Gains are 1.15 fractions; each sample the current gain moves by half the tracking rate times the distance to the target (current += 0.5 × rate × (target − current)), with the rate also a 1.15 fraction and 0 turning tracking off.
- **`+0x2c` is a band's target gain and `+0x28` its current gain, which glides to the target by itself (Confirmed, run 16).** After `+0x28` = 0 and `+0x2c` = `0x3e96` were written, `+0x28` read `0x48` at once, `0x3783` 100 ms later and `0x3e96` by 200 ms. The emulator uses `+0x2c` directly, which is right once the glide ends.

- **Read digitally (Confirmed, `pathprobe`, 2026-11-17).** With current and target set alike: the bypass alone passes the input exactly (`0x7fff` 8,192 → 8,192, `0x3fff` → 4,096, `0x8001` → −8,192); band 5 at `0x3e96` with the bypass added its band-pass on top (impulse 16,384 → 16,935, the extra 551 being b0 × gain); and the driver's ten band sections, read in the middle of a glide, summed to the model's arithmetic within 0.3% sample by sample. Not understood yet: with the bypass at 0, the bands alone gave silence when fed straight from a FIFO, but their normal sum when fed through mixer 6. Data: `data/pathprobe-20261117-1-eq.jsonl`, `data/pathprobe-20261117-2-eq.jsonl`.
- **The bypass gates the bands (Strong, `restprobe eqgate`, 2026-11-17).** With the bypass at 0 (current and target) the EQ gave silence whether fed straight or through mixer 6; with it at 1, the smallest step, the impulse came out as the band sum alone (12,947 against the model's 12,946); at `0x7fff`, the bypass plus the bands. So the output is the bypass term plus the band sum, but nothing at all when the bypass is 0. One reading in pathprobe run 1 (bands audible with a bypass target of 0 and its current word cleared) does not fit and is left open. The Windows driver never sets the bypass to 0. `lastprobe eq` then set the bypass and band gains as current/target pairs (held, gliding up, gliding down) with and without the EQ's time constants, 60 captures: the outcome depended on the history of earlier captures as much as on the settings (with the bypass at 0 the held bands were heard in one series and not the other; with the bypass gliding up from 0, nothing came through in any case with the driver's time constants). The EQ has internal state beyond the words written here, and this is left open. None of it reaches the Windows driver, which leaves the EQ at its pass-through. Data: `data/lastprobe-20261117-eq.npz`.

For an emulator driven by the Windows driver, a pass-through is exact; the band model above covers anything that programs the EQ itself.

### What the driver receives from the A3D library

Aureal's A3D library does not send filters to the driver. It sends one 1,036-byte control record per sound through a DirectSound property set, and Aureal's driver turns that record into the register values documented above. The layout below was read from the debug build of `a3dapi.dll` in the A3D 3.0 SDK (`Drivers/Debug`, built from a tree called "Anzio 3.0"), which is unoptimised and names its classes and source files in its assertion text: from the routines that fill the record, and from the library's own software renderer, which consumes the same record. (An earlier version of this section took the field list from the re-a3d-api reconstruction; the two agree.)

| Offset | Contents | Where it goes |
| --- | --- | --- |
| `0x04` | Mode: 1 = A3D (3D), 2 = native (2D) | 3D source or plain mixer path |
| `0x0c` | Frequency factor: the source's pitch × Doppler (3D only) × a global factor | Converter ratio or wavetable rate |
| `0x10` | High-frequency damping, 0 = none: 1 − (source EQ × global EQ × distance and occlusion factors in 3D), held between 0 and 0.99 | Atmospheric low-pass coefficients |
| `0x14` | Pitch multiplier applied to the buffer's sample rate (1.0 as initialised) | Converter ratio |
| `0x18` | 1.0 when the sound is not spatialised, else 0 | |
| `0x1c`, `0x20`, `0x24`, `0x28` | Left ear: azimuth and elevation in radians, gain, delay in seconds | `HrtfTarget` (looked up by the driver), `GainTarget`, `ITDTarget` |
| `0x2c`, `0x30`, `0x34`, `0x38` | Right ear: the same | |
| `0x40` | Audibility: (left gain + right gain)/4 + (1 − damping)/2 | Resource manager's ranking |
| `0x44` | Distance: the mean of the two ears' distances | |
| `0x50` + 56 n | Sixteen reflection entries of 56 bytes, each starting with an enable flag | Reflection voices |

What the routines show beyond the layout:

- **Each ear has its own direction.** The library computes azimuth, elevation and distance separately for the two ears and sends both.
- **The interaural delay is split evenly:** left delay = −ITD/2, right delay = +ITD/2, both zero when the sound is not spatialised.
- **Gain per ear** is that ear's gain × the source's gain × two further source factors × the global output gain; for a 2D sound it is the source gain × the pan value for that side × the output gain.
- **A source closer than 0.071 m is treated as inside the head:** the left ear's direction is set to +π/2 and the right's to −π/2, elevation and delays to zero.
- The record is kept in two copies and sent only when it differs from the one last sent.

So **the HRTF tables live in Aureal's driver**: the library never handles filter taps for a hardware source. An emulator that runs the original driver gets them for free; a wrapper that replaces the driver needs them. And **reflection delay is a time per reflection, not a register**: on the DirectSound route the library builds reflections by duplicating the sound buffer and starting the copy later, which matches the buffer restarts seen when the delay slider moved.

**The library's software renderer ("A2D") is not an HRTF renderer (Confirmed, same DLL).** It is what plays 3D sources the card has no channel for, and what cards without A3D get. It runs at 22.05 kHz and takes the same record. For each ear it looks the direction up in a built-in grid of 12 azimuths (30° apart) by 6 elevations (18° apart) plus two poles, 74 directions per ear with bilinear interpolation between the four nearest, and each grid point holds two 16-bit numbers: a level (about 0.2 to 1.0, highest toward that ear) and a filter amount that is zero on the near side and grows on the far side. With the two delays from the record that makes level difference, time difference and a one-coefficient head shadow, and nothing else: no pinna cues, no elevation or front-back colouring. It also multiplies each ear's gain by 1.5 before converting to 16 bits. That last figure may bear on the card: Aureal's map gives a one-bit right shift on the A3D outputs, and 1.5 × 0.5 is the 0.75 measured on the 3D path; where a 1.5 would sit in the driver's values is not known.

Logging these records during a traced session would give the driver's input and output side by side, and with them the exact conversions from gain, delay and `fAlpha` to register values.

## Routing, sample rates and timing

The Windows driver's audio graph, sample-rate arithmetic and master clock can now be read straight from snapshots and traces (`vortexprobe.py decode`).

### Routing (Confirmed)

The ADB route table is a set of linked lists. `CHNBASE` (`0x282b4` + channel × 4) holds each ADB channel's first route; a route is `source << 8 | sink`; `RTBASE` (`0x28000` + (route & 0xff) × 4) holds the next route; `0xffff` ends the list. This matches ALSA's `vortex_adb_addroutes`. Decoded from the idle, WAV and A3D snapshots:

| Function | Routes | Present |
| --- | --- | --- |
| Front output | `MIXOUT0/1` → `CODECOUT0/1` | Always |
| Rear output (4-channel codec) | `MIXOUT2/3` → codec sinks `0x8c/0x8d` | Always |
| S/PDIF | `MIXOUT8/9` → `SPDIFOUT0/1` (ADB channel 20) | Always |
| Hardware EQ loop | `MIXOUT6/7` → `EQIN0/1`; `EQOUT0/1` → `MIXIN7/8` | Always |
| Mixer feedback | `MIXOUT4/5` → `MIXIN1/2` | Always |
| Wavetable | `WT0_32/33`, `WT1_32/33` → `MIXIN3–6` | Always |
| Input monitor | `CODECIN0/1` → `MIXIN10/9` | Always |
| WAV playback | `ADBDMA0` → `SRCIN0/1` → `SRCOUT0/1` → mixer | While a sound plays |
| A3D sources | `ADBDMA2/3` → `SRCIN4/5` → `SRCOUT4/5` → `A3DIN15/14` | A3D demo |
| A3D output | `A3DOUT0–7` → `XTALKIN0, 5, 1, 6, 2, 7, 3, 8`; `XTALKOUT0/1` → `MIXIN11/12` | A3D demo |
| Extra wavetable voices (reflections) | `WT0_36/37`, `WT1_36/37` → `MIXIN14–17` | A3D demo |
| Second stereo stream | `ADBDMA1` → `SRCIN2/3` → `SRCOUT2/3` → `MIXIN0/13` | A3D demo |

So every A3D source passes through a sample-rate converter, the A3D engine and then the crosstalk canceller before the mixer. The always-present routes were also in the "cold" read, which means a warm reboot does not clear the route table: memory-like regions in that read hold leftovers from the previous Windows session, not true power-on contents.

### Sample-rate conversion (Confirmed)

`CONVRATIO` (`0x26e40` + converter × 4) is the input rate divided by 48 kHz, in unsigned fixed point with 14 fractional bits (`0x4000` = 1.0).

| `CONVRATIO` | Input rate |
| --- | --- |
| `0x3acd` | 44,100 Hz (the demos' WAV files) |
| `0x1d66` | 22,050 Hz |
| `0x1000` | 12,000 Hz |
| `0x0eb3` | 11,025 Hz |
| `0x0aab` | 8,000 Hz |

Doppler is applied here: during A3D play the moving source's converter is rewritten about 60 times per second with values from `0x3ac8` to `0x3ad1` (44,086–44,112 Hz). The test suite confirmed the formulas, with the A3D source on converter `0x26e5c`: `SetPitch(p)` settles at p × `0x4000` (0.5 → `0x2000`, 2.0 → `0x8000`), and a velocity v along the line of sight settles at c/(c + v) × `0x4000` with c = 343 m/s (+40 m/s → `0x3946`, −40 m/s → `0x4885`). The ramp is done by the driver, not the chip: it walks the ratio to the new value over about 8–9 writes (a few hundred milliseconds) instead of writing it once. The other converter words (`U0–U3`, drift) are not decoded; `U0`'s low byte is `0xc0` plus the converter number when in use. Unused converters and DMA channels hold random power-up contents. Non-3D playback at 8, 11.025, 22.05, 44.1 and 48 kHz gave `0x0aab`, `0x0eb3`, `0x1d66`, `0x3acd` and `0x4000`; 8-bit and stereo buffers changed no converter or DMA configuration word we could identify.

**Converter filter (Confirmed, run 12).** DirectSound buffers of noise, sweeps and single-sample impulses at 8, 11.025, 22.05, 32, 44.1 and 48 kHz were recorded and each compared with 48 kHz, which cancels the recording chain. Relative to the input rate the response is the same at every rate: flat to 0.45 × the input rate, −3 dB at 0.48, −6 dB at 0.50, −11 dB at 0.52, −23 dB at 0.55, −37 dB at 0.57, and below the recording's noise floor (about −60 dB) from 0.60. So the converter is a proper band-limited interpolator with its cutoff at the input's Nyquist frequency, and low-rate sounds come out with no audible images above it. 8-bit input and an arbitrary playback rate (22.05 kHz data played at 30 kHz) behave the same way. The filter is a Kaiser-windowed sinc, 27 input samples wide, with its cutoff at the input Nyquist: Aureal described the converter as a 27-point Kaiser-windowed sinc (relayed by the map's author), which is the 27-point interpolation of its feature comparison and the driver's 13 samples per wing. The window's parameter was read off the card: β = 8.6 (8.25 and 9.0 are both three times further from the data). A Blackman window (0.42 + 0.5 cos + 0.08 cos) over the same 27 samples fits exactly as well, 0.0040 rms, and was what the model used until Aureal's description was known; the measurements below were made against it and hold for either:

**Converter kernel read digitally (Confirmed, srcprobe 2026-11-17).** With the card idle on the host (no VM, `PCI_GCR` bit 21 cleared; see Clocks, interrupts and DMA), `tools/srcprobe.py` routed VDB FIFO 0 into converter 0 on the AC'97 sample rate, preloaded a single 16384 impulse, and read each output from the converter's output double buffer (`SRC_OUTPUT_DOUBLE_BUFFER`, two words per converter that take alternate outputs). At a conversion ratio of 1 the time fraction (`SRC_CHANNEL_PARAMS4`) stays where it is set, so each run gives the 26 taps at one phase exactly as the chip computes them; a sweep over 1,024 phases gave 492 clean ones (the rest lost or doubled a sample in the capture). At phase 0 the impulse comes straight through; at a half sample the taps are a symmetric ±10373, −3310, 1819, −1136 …; at every phase they sum to the impulse. A Kaiser-windowed sinc with **β 7.70 and half-width 12.85 samples** fits all 12,792 points to 0.65 LSB rms (3.99 × 10⁻⁵ of the impulse; 99% within 2.8 LSB), which is about rounding; the analog fit above (β 8.6 over 13.5) is 2.0 LSB off, and the two responses differ by under 0.2 dB up to 0.55 × the input rate. The emulator now uses the digital fit. The data are in `data/srcprobe-sweep-20261117.npz` and `tools/src_fit.py` repeats the fit. **Word length and rounding (Confirmed, srcprobe ampsweep 2026-11-17).** At two fixed phases (a half sample, and `0x1234`) the impulse height was stepped over 576 values from 1 to 32767. Every output of the 20 central taps at both phases, about 26,000 readings, fits **y = (C × x + 0x2200) >> 14** exactly, with one integer coefficient C per tap: the coefficients are 14-bit fractions (16384 = 1.0, so with sign the word is at least 16 bits), and the output is rounded to nearest with a constant of 0x2200, half an LSB plus 1/32 (an ordinary 0x2000 does not fit: heights where the exact product falls 0.47–0.50 above an integer round up). No single rounding of a real coefficient fits, which is why the four-height sweep looked inconsistent; the 14-bit coefficient explains it. The only misfits are the outermost taps, where the capture window overlaps the impulse's next pass through the 32-entry FIFO. Since a 16384 impulse gives y = C exactly, the main sweep's outputs are the coefficients themselves. Whether the chip keeps them in a table or computes them is not visible: at the sweep's resolution (1/1024 sample) their deviation from the Kaiser fit shows no step or interpolation pattern. **The full table (Confirmed, srcprobe 2026-11-17).** A sweep of all 16,384 time fractions (`srcprobe.py sweep --step 1`, about 4 minutes) gave the coefficients at every phase. Merged with the kernel's mirror symmetry (tap i of phase p is tap 25 − i of phase 16384 − p; of 266,480 values read on both sides, all but 44 agree exactly, and those 44 are capture errors), 209,716 of the 213,018 values in phases 0–8192 come straight off the card; 3,302 (1.6%) were lost on both sides and are filled from the Kaiser fit, and 78 isolated capture spikes were replaced by their neighbours' mean. Adjacent phases never differ by more than 2 in any tap. `tools/make_srctab.py` builds the table (`data/src-table-20261117.npz`) and the 86Box header from the sweep. The emulator now uses this table, indexed by the 14-bit fraction without interpolation, and rounds each output as the chip does, `(sum + 0x2200) >> 14`, with the sum exact in double precision. Checked against the ampsweep captures, it gives the card's outputs for every one of 962 impulse heights at two phases (five other captures were glitched), so a 16-bit stream through a converter comes out bit for bit as on the card. **Past full scale (Confirmed, srcprobe clip 2026-11-17).** Patterns of ±A with the signs of the half-sample taps (which sum to 2.26 in absolute value) give 18,533 at A = 0x2000, exactly as computed, and clamp to 32767 / −32768 at 0x3fff, 0x4800 and 0x6000; full-scale steps clamp the same way. At 0x7fff the peak (2.26 × 32767 = 74,075 LSB) comes out −32768 instead: the sum wraps before it saturates, which fits an accumulator of 31 bits (outputs beyond ±65,536 LSB change sign). The emulator does the same. The data are in `data/srcprobe-clip-20261117.npz`.

**Second sweep (2026-11-17).** `srcprobe.py sweep --phases` over the 1,712 fractions the first sweep left short, merged with it by `make_srctab.py`, brought the table to 212,622 of 213,018 values read from the card (99.8%); 396 are still from the fit and 18 are smoothed spikes. Of the 3,302 values the first build had filled from the fit, 2,911 were already right and the rest were off by 1. **Complete table (2026-11-17).** Two more passes over the phases still short (with the impulse at FIFO positions 8 and 16) and a better reading of the captures finished it. The converter's input is a 32-entry ring, so each impulse response repeats every 32 outputs (26 taps and six zeros); outer taps a capture missed at its start, or read as 0, are taken from their copy 32 outputs away, and an outer tap more than 3 LSB from the fit is dropped (a capture that lost a sample puts its copies one place out). Zeros are set aside wherever two readings agree on a non-zero value: across four sweeps, 2,843 of the minority readings were zeros of that kind against 331 non-zero ones. The result: all 213,018 values read from the card, none from the fit and none smoothed, with no value lacking a clear majority. Two more passes over the 1,114 fractions whose values rested on a single reading (impulse at FIFO positions 8 and 16) confirmed every one of them unchanged: in six sweeps, every value now rests on at least two readings that agree. Adjacent phases still never differ by more than 2 in any tap. The emulator's header and `data/src-table-20261117.npz` (with per-value vote counts) hold this table;

- **Impulses.** A single-sample impulse played at 8 or 11.025 kHz comes out as the kernel itself, sampled 6 or 4.4 times per input sample, and run 12 has eight of each. Dividing each lobe by the sinc gives the window's value there. From 3.5 to 11.5 samples out it follows the Blackman window over 27 samples to 0.004 rms with nothing adjusted. A three-term cosine window or a Kaiser window with every parameter free does no better (0.0037, 0.0039); Blackman over 26 or 28 samples, Hann, and the Kaiser window (β 8.25) the model used before are all worse (0.023, 0.023, 0.12, 0.014).
- **Transition band.** The same kernel gives the noise figures above to 0.5 dB.
- **Images.** In run 16 a 1 kHz tone at 22.05 kHz showed no image at 21.05 kHz down to −106 dB (the recording chain is 7.5 dB down there). The Blackman kernel puts it at −102 dB; the Kaiser kernel at β 8.25 (the model before run 12) at −87 dB, which would have stood 20 dB clear of the noise. β 8.6, the window now used, sits between the two (by a direct calculation of the kernels, 3 dB below β 8.25 and 6 dB above Blackman); it was not checked separately against this recording.

The same recording fixes the ratio word: the tone and its faint images at 2.9 and 4.9 kHz (−95 and −100 dB, the size 14- or 15-bit coefficients would leave) put the conversion ratio at 0.459350, and `CONVRATIO` was `0x1d66`, which is 0.459351 as a Q14 fraction. So 22.05 kHz material plays 53 ppm slow, and `SetFrequency` is applied by the driver as a ten-step glide of this word. Whether the chip normalises each phase's taps or interpolates between stored phases is not known; the model computes the taps directly (Strong). The map's author also expects the chip's conversions to be table driven, which would make the tables themselves readable with crafted inputs.

**Levels and headroom (Confirmed, run 12).** Output level is linear (full, half and one-tenth scale tones measured 1 : 0.499 : 0.100), the converter has unity gain (a half-scale tone at 22.05 kHz matched 48 kHz within 0.04 dB), and an A3D native source and a 3D source straight ahead at the minimum distance in headphone mode both play at the source's own level. Summing half-scale tones of different pitches showed that the output saturates at digital full scale: two tones (peaks reaching full scale) stayed clean, three left distortion products 29 dB below the signal with the peaks held at full scale, and four 15 dB below. The output does not wrap around.

### DirectSound buffers and the mixer (Confirmed, run 2)

Ordinary DirectSound hardware buffers, the path most non-A3D games use, map onto the chip like this:

- **Volume and pan** go to mixer input gains: targets at `0x212xx`, current values at `0x202xx`, one word per input per output side (for example `0x21238` left and `0x212b8` right). The word is a gain byte with `0x08` = unity (measured 0.0 dB against the plain playback path); Aureal's description of the mixer (relayed by the author of a register map of the chip) gives it as a signed 5-bit exponent and a 3-bit mantissa, the fixed-point number .1MMM × 2^EXP: `0x08` = unity, `0x2f` = 30 (+29.5 dB) the largest, `0x80` = −102.35 dB (mute), steps of 0.56–1.02 dB within each 6 dB octave. The map's author also supplied the full table of the 176 codes from `0x80` to `0x2f`; the model matches every entry to within the table's rounding (0.0004 dB). The map itself describes the byte's low field as the three low bits of the mantissa, which agrees with the table. Run 16 settles the mantissa on the card: DirectSound volume steps on a 1 kHz tone held the mixer inputs at `0x08`, `0x03`, `0x00`, `0xf8` and `0xe8`, and the recorded levels relative to `0x08` were 0.68749, 0.50000, 0.25000 and 0.0625. `0x03` is .1011 = 0.6875; a repeated mantissa would have given 0.714. So the mixer does not repeat the mantissa, unlike the wavetable bytes, as the map's author also recalls (Confirmed).

**Gain changes (Aureal's description, relayed).** The mixer has no ramp of its own. A current gain takes its target's value in one step at the next zero crossing of the signal it scales (the chip stores the previous sample's sign beside each current gain). Smoothing is left to the driver, and the traces show it: for a DirectSound volume or pan change the Windows driver walks the target through intermediate codes about every 7 ms. The emulator switches at the zero crossing; it also treats a sample of exactly zero as a crossing so that a silent input does not hold a stale gain. The same description gives the pipeline: each 16-bit input times its gain, summed with 5 bits of headroom and clamped at ±32 × full scale (setting an overflow flag); the output gain applied as its exponent shift, clamped at ±2, then its mantissa, and the result clamped to full scale (setting a saturation flag). DirectSound volumes map to codes as −600 mB → `0x00` (−6.0 dB), −1200 → `0xf8`, −2400 → `0xe8`, −4800 → `0xc8` (−48.2 dB), −10000 → `0x80` (silent); a Windows mixer slider at the top also gives `0x00`. Pan attenuates only the opposite side, with the same law.
- **Frequency** goes to the buffer's converter as frequency / 48 kHz × `0x4000`, ramped by the driver over about 10 writes (24 kHz → `0x2000`, 96 kHz → `0x8000`).
- **Sample format** is in the ADB DMA control word (`0x27a00` + channel × 4): `0x22000` for 16-bit and `0x6000` for 8-bit. Read with ALSA's field layout, bits 14–17 hold 8 (signed 16-bit) or 1 (unsigned 8-bit). Mono versus stereo is not in that word; stereo buffers get a second route.
- 8 kHz buffers were refused in hardware (DSERR\_ALLOCATED) and fell back to software mixing; 11.025–48 kHz were all accepted.

**Sound Blaster in a DOS window (Confirmed, Duke Nukem 3D setup).** Sound Blaster emulation in a Windows 98 DOS window is done in software by Aureal's driver, which plays the game's audio through the ordinary playback path: an ADB DMA channel → sample-rate converter → mixer, the same route DirectSound uses. The converter is set to exact Sound Blaster time-constant rates: 10,989 Hz (time constant 165), 21,739 Hz (210), 10,752 Hz and 6,000 Hz. The DMA control word is `0x7000`, which is unsigned 8-bit with the DMA interrupt enabled; ordinary Windows playback leaves it off. So the driver apparently points the card's DMA at the DOS program's own 8-bit buffer and uses the DMA interrupt to raise the emulated Sound Blaster interrupt. No legacy I/O-port decoding by the card is involved, so an emulator running Aureal's Windows driver gets DOS-window Sound Blaster support with no extra hardware model. BAR2 was touched only at boot (one write/read/write at offsets 4 and 6). Selecting General MIDI crashed the setup program. Real-mode DOS (Restart in MS-DOS mode) is untested.

**Sound Blaster test program (Confirmed, sbpro session 2026-11-01).** A small test program (DSP reset at 220h, version query, one second of single-cycle 8-bit DMA at 11 kHz on DMA 1, mixer master volume) passed three times in a Windows 98 DOS window: DSP version 3.02, IRQ 5 delivered, DMA count exhausted, and the tone audible in the recording. During playback the driver touched no register outside the ordinary wave path: ADB DMA channel 0 cycled through four 1 KB pages, with the page-done interrupt raising the emulated IRQ. A replay of the whole session through the 86Box model matched every register read the driver made in that window.

**Boot-time Sound Blaster set-up (Strong).** When Sound Blaster emulation is enabled, something runs at boot, before the Windows driver loads, and talks to the card through the I/O window (BAR1). It sets bit `0x01000000` in `CHIP_CTRL` (`0x2a00c`), plays ADB DMA channel 1 from four 256-byte pages in low memory (`0x6500`–`0x68ff`) through a sample-rate converter to the mixer, briefly enables the timer interrupt, then masks every interrupt and leaves `CHIP_CTRL` at `0x01103260`. The Windows driver later reads the top byte of `CHIP_CTRL` (1 when emulation is on) and writes `0x212eb` to `0x2a804`. The meaning of bit `0x01000000` and of `0x2a804` is unknown; they may enable the chip's own legacy port decoding for real-mode DOS. Real-mode DOS (outside Windows) cannot be tested under QEMU passthrough, because QEMU does not forward legacy ISA ports such as 220h to the card; it would need bare metal.

**Real-mode DOS: the chip has a Sound Blaster front end (Strong, from AU30DOS.COM 2.007).** `AU30DOS.COM` ("Vortex DOS audio driver", 1997–99) is a resident program for plain DOS that refuses to load under Windows, reads its settings from `AU30DOS.INI` (`sbfmbase`, `sbfmirq`, `sbfmDMA`, `FMBase`, `joystickbase`, `mpu401base`) and sets `BLASTER`. It contains no protected-mode or V86-monitor code and does not use EMM386's port trapping; it only asks VCPI (`int 67h`, `DE00`/`DE0B`) where the interrupt controller's vectors are, to hook its interrupt. The port decoding is the chip's own, set in the control word `0x2a00c`: bits 0–4 and 14 are enables (MIDI, game and three more), bits 7–8 select the Sound Blaster base (`220h`, `240h`, `260h`, `280h`), bits 9–11 the game port (`200h` + n), and its unload routine clears bits 0–4, 14 and 19. The chip latches what a DOS program does to those ports in a block at `0x29840`–`0x29854`: `AU30DOS` reads `0x29840`, `0x29844` and `0x29848` as bytes, acknowledges flags in `0x2984c` by writing a mask, and writes two bytes into `0x29850` (whose reset value `0x302` is the DSP version 3.02), so the DSP's command handling is the resident program's while the port decoding, latching and read-back are hardware. Five interrupt-source bits are its signals (`0x20`, `0x80`, `0x100`, `0x1000`, `0x4000` in `0x2a000`, enabled in `0x2a004`). `0x29854` (bit 8) and the 64 words at `0x29900` are read together in what looks like the FM path. `sbprobe.py` maps these registers on the host; the ports themselves cannot be exercised on the X79 (no legacy I/O forwarding). For 86Box this means real-mode DOS Sound Blaster on the Vortex needs that front end modelled; Windows DOS boxes do not use it.

**The FM side is hardware: OPL decode, register file and timers (Confirmed, `sbprobe` 2026-11-18).** The X79 forwards ports `388h`–`38Bh` to the card, so the FM front end could be driven from the host. With the control word at AU30DOS's `0x0118326e` the chip answers at `388h` (status `0x00`; `0xff` with the decode off, and `0xff` from `38Ah`, as an OPL3 reads). Writing an index latches it in the low byte of `0x29854` (bit 8 follows the OPL3 enable bit of register `0x105`), and `0x2985c` shows the index with the last data byte in bits 23–16. Each data byte lands in a packed register file in the 256 bytes at `0x29900`, one byte per register an OPL3 has (`fmmap`, every index of both banks): bank 0 puts `0x01` at 0x00, `0x08` at 0x01, the operator groups `0x20`, `0x40`, `0x60`, `0x80` at 0x02, 0x14, 0x26 and 0x38 (18 bytes each, operators in order: register offsets 0–5, 8–0xd, 0x10–0x15), `0xa0`–`0xa8` at 0x4a, `0xb0`–`0xb8` at 0x53, `0xbd` at 0x5c, `0xc0`–`0xc8` at 0x5d and the `0xe0` group at 0x66; bank 1 the same 0x78 bytes on (`0x101` at 0x78, `0x104` at 0x79), and every other register, `0x105` included, lands in one byte at 0xd4. A key-off write to `0xb0`–`0xb8` (bit 5 clear) is stored with bits 7–6 set, and reading the word clears them; a key-on write is stored as written (`fmflag`: `0x05` over `0x25` read `0xc5` once and `0x05` after, unread it stayed `0xc5` for 20 ms, and `0x25` never gained a flag). Writing `0xbd` with rhythm off (`0x5a`) flags channels 6–8 the same way; with rhythm on (`0x3f`) it left them alone. So the renderer, which polls the file and never writes it, sees each key-off once. Bank-1 writes are kept only in OPL3 mode (with `0x105` clear the file did not change). The legacy decodes also need I/O space on in the card's PCI command register, which AU30DOS sets itself (it ORs 5 into it); a probe run after a power cycle, with only memory decoding on, read `0xff` at `388h` whatever the control word held. The `0x30` bytes AU30DOS and the Windows driver write at 0x5d–0x65 and 0xd5–0xdd are each channel's output bits (left and right on). Writing to the ports raised no interrupt; a timer running out sets bit `0x40` of `0x2a000`. **The timers are real:** the AdLib detection sequence (reset, timer 1 at `0xff`, start) read `0x00` and then `0xc0`; timer 2 gave `0xa0`, a masked timer left the status at 0, and timer 1 from 0 ran out after about 20.5 ms, 256 steps of 80 µs (Confirmed). So DOS programs detect an AdLib or OPL3 from the chip itself, and the register file is what software reads to synthesise the sound. Ports `220h`–`22Fh` did not answer with any control-word bit tried (bits 0, 4, 14, 19, 24 and the driver's `0x2a804`), most likely because this board does not forward them; the Sound Blaster DSP side is still mapped only from AU30DOS. The Windows driver sets the same control word (`0x118326e`–`0x118726f` in every A3D trace), so a DOS box under Windows also gets FM detection from the chip. The 86Box device models the decode, the register file, the latch and the timers (`7212635e` on `vortex2`); the FM ports are control-word bit 2 (`sbprobe fmbit`: `388h` answers with bit 2 alone added to the reset word and stops when only bit 2 is taken from AU30DOS's word; bits 1, 4, 19 and 24 have no effect on it). Bit 1, set with it by AU30DOS and the driver, is probably the Sound Blaster ports (Hypothesis: they are not forwarded here).

**Resource conflict that freezes the machine (Confirmed in an 86Box VM).** The emulation reserves fixed legacy resources: I/O 220–22Fh, IRQ 5 and DMA 1. Device Manager offers only one basic configuration, and Windows will not let the IRQ be changed even with automatic settings turned off. If Windows' ACPI IRQ steering has put a PCI device on IRQ 5, the two collide. In an 86Box ASUS P2B-LS machine the Intel 82371AB/EB USB controller sat on IRQ 5 (Device Manager listed it, with the ACPI IRQ holder, as the conflict), and with Sound Blaster emulation enabled Windows froze at boot just after the startup sound; disabling the emulation fixed it at once. Because the emulation is Aureal's own driver code, a real SQ2500 in the same board should behave the same way. The fix is to disable Sound Blaster emulation in Device Manager, or to move the other device off IRQ 5 (disable it, or reserve IRQ 5 for legacy ISA in the BIOS where that is offered).

**Recommendation for emulator users.** The Vortex's Sound Blaster support is a software layer for DOS windows, compatible only to Sound Blaster Pro (DSP 3.02), and it costs a fixed IRQ that can collide with PCI devices. For DOS games, an emulated Sound Blaster 16 or similar ISA card is the better choice; leave the Vortex's Sound Blaster emulation disabled unless something specifically needs it.

**MIDI is software synthesis (Confirmed, run 12).** The driver offers two MIDI devices, "Vortex AU8830 MPU-401" and "Vortex AU8830 Wavetable" (576 voices). The wavetable device does not use the chip's wavetable voices: during a full MIDI test (notes across the keyboard, velocities, eight instruments, drums, controllers and 40 s of CANYON.MID through the MIDI mapper) no voice parameters or wavetable DMA were written. The driver renders the music on the host and streams it as PCM through ADB DMA channel 0, driven by a fast sample timer (periods of about 0.3–1.7 ms, roughly 500 interrupts a second). It also polls word `+0x10` of each wavetable bank (all ones on the real card) and writes `0x00880000` to `+0x04` about 100 times a second. An emulator that plays DMA streams and services the timer therefore reproduces the MIDI output exactly, with no instrument model.

### Wavetable voices in a game (Half-Life, A3D mode)

Five minutes of Half-Life play (session `20261031-203721-hl-play2`, interrupts alive throughout) used the wavetable engine far more than any earlier test. About 8,700 sounds started in five minutes, each on its own voice in the second half of the engine (voices 4–29 at `0x8200` + voice × 0x10, with wavetable DMA channel 32 + voice). Up to 28 voices were active at once, alongside about 12 of the 16 A3D sources. Voice starts did not coincide with A3D source starts or with ADB DMA starts. DirectSound in our test suite used ADB channels and converters instead, so this is a separate path.

**DirectSound's advertised 3D buffer count depends on Sound Blaster emulation (Confirmed).** With SB emulation enabled in the Aureal settings, `AU30DOS.COM` (run from `AUTOEXEC.BAT`) initialises the chip before Windows: it leaves the chip control register (`0x2a00c`) with bit 24 set, the Windows driver reads that byte (`0x2a00f`) at start-up, and DirectSound reports 76 hardware 3D buffers. With SB emulation disabled, `AU30DOS.COM` stops with "ERROR #6: Sound Blaster Emulation disabled in Windows", the register is still at its reset value (`0x00303260`), the driver takes another start-up path, and DirectSound reports 16. Minerva's Max Out finds 76 mono 3D sources either way, so only the advertised number changes. Compare emulator and card with the same setting.

**`0x22034` is read-only and reads `0xff` (Confirmed, five real traces); it is the driver checking for the SQ3500's DSP (Plausible, see the SQ3500 section).** At start-up the driver writes 0 there and reads it back; the real card returns `0xff` and the driver moves on. A register that holds its value sends the driver into a long write-and-read test (13,787 writes in 86Box before the fix). Minerva's Max Out then found 7 stereo 3D sources instead of 9. `0x2205c` (`SPDIF_FLAGS`) reads `0x138015` at start-up (`0x138014` in some sessions), and bit 0 stays set when it is written.

**FIFO control readback on an idle channel (Confirmed, three real traces).** Written `0x41000`, it reads `0x41020` (0x20 = empty); written `0x42000`, it reads `0x42060`, so the card adds 0x40 whenever bit 13 is set. The driver's DirectSound path waits for 0x40 before setting the start bit (0x10): Minerva's streaming buffer never started in 86Box until the emulator returned it. The plain wave-out path just adds 0x10 to whatever it reads.

**Fetch pattern (Confirmed, Half-Life sessions).** A playing channel's status word (`0x27d00`/`0x27e00` + channel × 4) holds the fetch pointer's byte position (bits 11–0), the page (bits 13–12), the samples played since the last fetch (bits 19–14) and the run state. The card prefetches 56 samples when a stream starts (position `0x070` within 0.15 ms of a 16-bit start) and then fetches 18 samples each time 18 have been played (position steps of `0x24`), so the samples-since-fetch field cycles 0–17: in 393,000 running-channel reads over two sessions it was 0–2 in 17–21% and 3–17 in 79–83%, and above 17 in 0.1%. The driver polls these words thousands of times a second to locate the play position, so an emulator should fetch the same way.

**What the status word's upper bits mean (Plausible, register map).** The map names bit 23 "transfer in progress" (with bits 31–24 the bytes still to go), bit 22 FIFO empty, bit 21 FIFO valid and bits 20–14 the samples the FIFO wants (7 bits). The run states above read in those terms: 2 (running) is valid with a few samples wanted, 0 (draining) is neither valid nor empty, and 5 (idle, `0x5…`) is empty with 64 wanted, the whole FIFO. The "samples since the last fetch" count is the wanted count, which the 18-sample fetches keep below 18. The emulator's DMA completes at once, so it never shows bit 23. The FIFO control words (`0x16000`/`0x16100` + channel × 4) hold, per the map, a write mask in bits 31–22 (so `0x1c4…` then `0x0c4…` are commands, not values), flush (21) and freeze (20) strobes, a fault flag (19), wait-for-DMA (18), the DMA and FIFO pointers (17–12, 11–6), empty (5), valid (4), priority (3–2), stereo (1) and DMA request (0); readback is bits 19–0, as measured. A FIFO trigger register at `0x17000` sets the level at which a FIFO asks for data (bits 6–1) with an optimisation enable (bit 0); the driver writes `0x00042061` at start-up (Plausible). How that value yields the measured 56-sample prefetch and 18-sample refills is not worked out, so the model fetches by the measured pattern. The map's author confirms 18 is the driver's choice, and attributes many of the pops, clicks and swapped-stereo faults known from real cards to the driver's FIFO and DMA handling.

Starting a voice: the driver clears the voice's 64-word FIFO (`0x10000` + global voice × 0x100) and its FIFO control word (`0x16000` + global voice × 4), and sets up the wavetable DMA ring (`0x27000`/`0x27600`/`0x27900` + channel). It then reads and clears `0x8008` and `0x8080` + (voice ÷ 2) × 4, and writes PARM0–3. While the voice plays, the driver writes 0 to `0x8180` + voice × 4 at each DMA refill. A register map of the chip names these: `0x8008` is `DSREG` (below), `0x8080` holds a flag per even/odd voice pair that makes the two start on the same sample (cleared here, so voices start singly), and `0x8180` is the voice's running flag. The DMA control word is `0x22000`, which means signed 16-bit. The clear matters: a stopped channel plays out what its FIFO holds, so after the driver zeros it the play-out is silent. Half-Life restarts footstep voices constantly and zeros the FIFO each time; a model that keeps its own FIFO copy has to clear it on those writes or it plays the previous sound's tail (heard as pops while walking). After the driver stops a voice, the card reports it draining (status top nibble 0) while the FIFO plays out at the voice's rate, then idle (`0x5`): median 5.5 ms, 10th–90th percentile 2.5–14 ms in Half-Life, whose voices run at 11 and 22 kHz, so about 56–64 samples (Strong).

**PARM0/PARM1 layout (Strong).** In steady state PARM0 and PARM1 are the same apart from bit 0 (0 in PARM0, 1 in PARM1). A register map of the chip explains the pair: PARM0 is the voice's base word and PARM1 its target word, and bit 0 of each is a state bit. While the two state bits are equal the chip glides pitch, gain and cut-off from base to target along the half's ramp register (`0x0004`/`0x8004`: slope in the upper half, position in the lower); while they differ it uses the base word alone. The driver always writes them differing (every pair in the traces), so the base word is the voice's setting and the ramp is idle. The emulator reads the base word only and does not model the glide.

- **Bits 1–15: playback rate (Confirmed).** A 3-bit exponent over a 12-bit mantissa: e = bits 13–15, m = bits 1–12, rate = 48 kHz × 2^(e−5) × (1 + m/4096). With e = 0 there is no leading one (rate = 48 kHz × m/65536, by the same expansion rule as the gain byte), which only matters below 3 kHz. Whether the chip also repeats the mantissa below its last bit, as it does for the gain byte, cannot be told from the traces: it would move the rate by 0.01%. This was checked against the measured DMA consumption for 41 distinct values. The mean ratio of measured to predicted was 1.000 with a 2% spread, which is the measurement noise, and no constants were fitted. Examples: `0x5acc` = 11,025 Hz, `0x7acc` = 22,050 Hz, `0xa000` = 48 kHz. The last is the value the reflection voice used in the test suite. Half-Life's values cluster around 11,025 Hz with a few percent spread, which matches the game's randomised pitch. **The step is a 0.16 fraction with the mantissa repeated (Confirmed, run 18).** The tones of run 18 give each rate word's actual rate to a few parts per million: `0x4aaa` 7999.57 Hz, `0x4c18` 8267.60, `0x5acc` 11025.30, `0x6636` 14329.20, `0x7acc` 22051.20, `0x8aaa` 31999.85 and `0x9acc` 44102.45 (recorder's clock). Read as 1 + m/4096 these come out 3 to 109 ppm high, a different amount for each word. Read as the chip's other codes are, an implicit leading one followed by the mantissa repeated, shifted by e − 5 and cut to 16 fraction bits (`0x9acc` → `0xeb36`, `0x5acc` → `0x3acd`), all seven come out 3–14 ppm high, which is the recorder's clock. So a "44.1 kHz" voice runs at 44,102.05 Hz, not 44,097.66. The emulator steps voices by this 16-bit value.
- **Bits 16–23: gain**, on the same log scale as the reflection gain (`0x10` per 6 dB). The byte is a 4-bit exponent over a 4-bit mantissa. Aureal's method, relayed by the author of a register map of the chip, expands it to a linear value: an implicit leading one, then the mantissa's bits repeated to fill every place below it (exponent 0 is the mantissa alone). That puts `0xcf` at exactly `0xffff`, which is why it is unity. It also inverts the driver's encoding: the reflectance steps above (0.75, 0.35, 0.1 below `0x93`) decode to 2.50, 9.19 and 19.96 dB, the amounts asked for, and the measured echoes agreed within their 1 dB scatter. The expansion stays within 0.4 dB of a smooth 2^((g − `0xcf`)/16), which the emulator used before (Strong). `0x00` is silent. New voices fade in over about 25 ms (`0x00` → `0x5c` → `0x6c` → `0x75` → `0x7b` …). Typical playing values are `0x8a`–`0x9c`, and the ceiling is `0xcf`.
- **Bits 24–31: filter cut-off (Confirmed, run 19).** The voice's low-pass is four one-pole stages in series, each y += F × (x − y), where F is this byte expanded like the gain byte (implicit leading one, mantissa repeated) and read as a fraction of 65536. `0xcf` gives F = 0.99998, which is why it is "open"; `0xc0` is F = 0.5, `0xb0` 0.25, and so on down. So the response is 24 dB per octave well above the corner, and the corner (−3 dB) is near 0.07 × F × 48 kHz for small F: about 830 Hz at `0xb0`.

  Run 19 measured this directly. `A3DTEST wtnoise` put steady 48 kHz noise on a second-half wavetable voice and `vortex-poke.py wtfilt` stepped the byte from the host through 27 values (`0xcc` down to `0x80`, and `0xb1`–`0xbf`), each compared with the untouched voice in the same recording. With nothing fitted, the four-stage filter matches all 27 responses to 0.36 dB rms (bands down to −30 dB). Fitting a free coefficient per step gives 1.000–1.010 × the expanded byte wherever the fit is clean. Two, three or a bilinear Butterworth four do not fit (2–7 dB). `0xbf`, `0xaf` and `0x9f` measured the same as `0xc0`, `0xb0` and `0xa0` (within 0.2 dB), which shows the mantissa repeating.

  This replaces the earlier reading from run 14 (a second-order filter, Q 0.64, with a fitted cut-off curve). Run 14 only had each setting relative to another through a reflection, which could not separate the orders; the map's author had it right that the filter is fourth order.

  **Feedback (Confirmed, run 19b and `wtprobe reso`).** The second voice word's upper half (`PARM2` bits 31–16) adds resonance around the four stages. Run 19b measured it in noise: With the cut-off at `0xb0` (F = 0.25) and at `0xa0` (F = 0.125):

  | 0 (the driver's value) | 0 dB | none |
  | `0x1000` | −13.5 dB | +0.9 dB at 2.27 kHz (F = 0.25); +5.2 dB at 1.03 kHz (F = 0.125) |
  | `0x2000` | −13.0 dB | −0.2 dB; +2.9 dB |
  | `0x3000` | −12.7 dB | −1.2 dB; +2.0 dB |
  | `0x3800` | −12.3 dB | −1.3 dB; +1.5 dB |
  | `0xe000` | −3.4 dB | none |

  It is a ladder: the last stage's previous output is fed back to the first stage's input, u = x − k·y[n−1], with k = (−word mod 2^16) / 2^14. So 0 is off, `0xffff` almost off, `0xe000` 0.5, `0xc000` 1, `0x8000` 2 and `0x0400` 3.94. The pass band falls to 1/(1 + k): −13.5, −13.1, −12.6 and −12.3 dB for `0x1000`–`0x3800` and −3.5 dB for `0xe000`, the table's levels. The resonant peaks this gives are +0.7 dB at 2.29 kHz and +5.5 dB at 1.03 kHz for `0x1000`, and −0.4/+3.4, −1.3/+1.7 and −1.7/+1.0 dB for the next three, all within 0.5 dB and 20 Hz of the table. (An earlier fit, with k free per value and no delay in the loop, missed by 2 dB.) `wtprobe reso` (2026-11-17) checked it digitally: a 32-sample step through cut-offs `0xb0`, `0xb8` and `0xc0` at 16 words fitted k within about 0.15 of the law at every word. With the filter open (`0xcf`), where the four stages pass everything, the loop is a single delay: `0xe000` gave 2/3 of the level, `0xc000` a steady tone at half the sample rate, and every word with k above 1 gave silence. The emulator models this (feedback with the filter open, and silence where the open loop would run away). Data: `data/wtprobe-reso-20261117.jsonl`, `.npz`.

  **Gain codes, input gain and pan (Confirmed, run 19b).** The same run stepped the other fields under the same noise. Gain bytes `0xce`, `0xc8`, `0xc0`, `0xbf`, `0xb8` and `0xb0` gave 0.970, 0.766, 0.502, 0.501, 0.383 and 0.251 of the level at `0xcf`; the expansion with the mantissa repeated gives 0.967, 0.767, 0.500, 0.500, 0.383 and 0.250. The filter input gain (`PARM3` bits 31–24) uses the same code and acts ahead of the filter: `0xbf` and `0xaf` gave exactly 0.501 and 0.250 at every frequency, with the filter open or closed. The pan field does nothing to a voice that feeds an A3D source (`0x00`, `0x20` and `0x7f` all within 0.03 dB).

**Interpolation (Confirmed, run 18).** A wavetable voice playing away from 48 kHz interpolates with the cubic Lagrange polynomial through four input samples (Aureal documents "4 point interpolation"). Run 18 forced a 3D tone onto a wavetable voice by occupying the ADB channels with twelve silent sources first: the tone took second-half voice 5, at rate words `0x4aaa` (8 kHz), `0x5acc` (11.025), `0x7acc` (22.05), `0x8aaa` (32) and `0x9acc` (44.1 kHz). Each tone was 0.2 × the rate, so the interpolator's images fell in band. Simulating each candidate end to end at 48 kHz (images fold onto one another there) and correcting for the front HRTF, the 46 measurable lines matched cubic Lagrange with a median error of 2.2 dB (2.2 dB rms over the 22 lines at 11.025 kHz). Catmull-Rom, which the model used before, was off by a median 7.4 dB and up to 20 dB; linear and cubic B-spline interpolation are far off (13.7 and 22.5 dB). A second pass over the same recording resolved every image line on its own (a 3 s window; the rate words are slightly off the nominal rates, see the rate field above, so images that would fold onto one frequency sit a few hertz apart). At 8 kHz that gives nine ratios between images landing within 3 Hz of each other, which need no HRTF correction: they match cubic Lagrange to 0.8 dB rms out to the eighth image, and a coefficient table of 32 or fewer phases is excluded (1.1 dB rms at 32, 2.6 at 16). The earlier report of three 8 kHz images 6–10 dB low came from measuring such pairs unresolved, and the "40 dB low" image of the 44.1 kHz step from looking at the nominal 16,620 Hz when the line is at 16,615.5 Hz. That line (the second image, 1.8 × the rate) is still about 6 dB under lines from other steps 30–140 Hz away, at 61 dB below the tone; the same image at 22.05 and 8.27 kHz is about 2 dB under. Not explained, and too small to matter by ear. The emulator uses cubic Lagrange. (The map's author recalls a "4-point linear interpolation". Straight-line interpolation between two samples does not fit, at 13.7 dB; a cubic through four points is linear in the samples, which may be what is meant.)

**Pan of a native A3D source (Confirmed, run 18).** `SetPanValues` on a native (2D) A3D source is done with mixer input gains, not the voice's pan field, and is linear: per-channel values 1, 0.5, 0.25 and 0 became `0x08`, `0x00`, `0xf8` and `0x80`, and the recorded levels were 1, 0.500, 0.250 and silence. **PARM2 and PARM3 (register map, checked against the traces).** PARM2 holds the filter's feedback gain (bits 16–31, 2.14 fixed point; the resonance) and the pitch oscillator's phase (bits 0–15). The driver always writes 0: no resonance, phase reset. PARM3 holds:

- **Bits 24–31: filter input gain**, in the gain byte's code. Always `0xcf` (unity).
- **Bits 21–23: gain state.** 0 is a hard mute and 7 is normal playing; 2, 3, 5 and 6 are the attack and smooth-mute ramps (below), timed by two ramp registers. Across the test suite and Half-Life the driver wrote only 7 (193,000 times) and 0 (at reset), and does its own 25 ms fade-in through the gain byte.
- **Bits 14–20, 7–13, 0–6: pan, chorus send, reverb send** (see the bus section below).

That decodes the constant `0xcfef` in the high half: unity input gain, normal state, pan `0x3f` (centre). The emulator applies the input gain, the states and the ramps; and the resonance.

**Bus headroom arithmetic.** The map gives the sum exactly: each voice produces a 20-bit sample, 32 voices sum to 25 bits, and the 16-bit bus output is bits 24–9 of the sum shifted left by the headroom setting. Headroom 5 is therefore unity for a single full-scale voice. The driver's 6 on the direct-stream pair is ×2 and its 2 on the other buses is ×1/8. Since a direct-stream voice at gain `0xcf` and centre pan measured exactly unity (run 16), the voice's 20-bit sample is at half scale there. A linear pan with 0.5 on each side at the centre would do that, which supports the linear crossfade the emulator assumes. The map's author confirms that the pan acts on the voice's data ahead of both pairs and that pan and the two sends are 0.7 fixed point (`0x7f` just under 1, `0x3f` just under one half); he describes the pan as a crossfade, which supports the linear crossfade the model uses; that it is linear in the codes is not measured. The driver never moves the field: DirectSound pan and volume on a wavetable voice are done with the mixer input gains (run 16).

**Test-suite run 11 (`wtpath`, Satellites) sorted out the two kinds of wavetable voice (Confirmed).**

- **Reflections are always first-half voice 0, playing at the source's own rate.** One click source with a reflective wall gave a rate field of `0xa000` for a 48 kHz source, `0x7acc` for 22.05 kHz and `0x5acc` for 11.025 kHz. At pitch 0.5 the field glided down to about `0x3b78`, roughly half. Gain stayed at `0xa0` and the top byte at `0xc6`, as in the earlier runs. The voice's DMA pages pointed into the same host buffer that the source's ADB channel was playing from. So the reflection is the source's own sample data, fetched a second time at a start offset the driver picks; that offset is the most likely place the reflection delay lives (Strong).
- **Second-half voices 0–3 feed A3D sources once ADB channels run out.** Sixteen sources were started 250 ms apart. The earlier ones took the free ADB channels (3–13, each feeding one A3D slot from 14 down to 4), and once those were used up the last four took second-half voices 0, 1, 2 and 3, one per source, each started at the same instant as its A3D source (slots 3, 2, 1, 0). Those voices ran at the source rate (`0x7acc`, 22.05 kHz) with gain and top byte fixed at `0xcf`. So a wavetable voice can stand in for an ADB channel as an A3D source's input, at unity gain.
- **Extra sources steal slots; they do not overflow to wavetable voices.** Each louder click added on top of the 16 quiet sources took over an existing A3D slot (slot 0, then 1, 2, 3, 4 …). No further wavetable voices were used.

So Half-Life's second-half voices 4–29 are neither reflections nor A3D overflow. They carry their own gain and filter and start independently of A3D sources, which fits ordinary (non-3D) sound buffers played on wavetable voices once the ADB channels are busy (Hypothesis). The route table did not change during play, so their routes were set when the driver loaded.

**Voice output routing.** Each half has 32 per-voice sources (`0x40` + voice for the first half, `0x80` + voice for the second) and three mixed-output pairs, 32/33, 34/35 and 36/37 (`0x60`–`0x65`, `0xa0`–`0xa5`).

- **A voice whose own source is in the route table plays only into that route (Strong, from the emulator).** In A3D mode the driver feeds 3D inputs this way, at unity gain. Before the emulator did this, voices feeding A3D sources also leaked into the plain stereo mix in Half-Life.
- **Otherwise `DSREG` (`0x0008` in each half, one bit per voice) picks the mixed-output pair: set = 32/33 (Confirmed).** Test-suite run 16 played DirectSound buffers with A3D closed. The driver put them on first-half voices 0–25, set their `DSREG` bits (`0x3ffffff`) as it started them, and routed only 32/33 (`0x60`/`0x61`) to the mixer. Clearing `DSREG` from the host under a playing voice silenced it (about 87 dB down); restoring it brought the voice back; setting every bit changed nothing.
- **Clear = the main pair 34/35 plus reverb (36) and chorus (37) sends, 24 dB down (Plausible, register map with Half-Life traces).** A register map of the chip names a half's six outputs as direct-stream left/right (32/33), left/right (34/35), reverb (36) and chorus (37), and puts a voice's pan (bits 20–14), chorus send (13–7) and reverb send (6–0) in `PARM3` (`0x20c`). Half-Life in A3D mode writes the second half's `DSREG` as 0, plays ordinary sounds on second-half voices 4–29 without routing them, never routes 34/35, and routes 36 (`0xa4`) to the left mix and 37 (`0xa5`) to the right through mixer inputs `0x5d`/`0x5e`. On a real card its `PARM3` writes keep the pan field at the centre (`0x3f`) and set the two send fields per sound, mostly at or just below `0x7f` (`0x7d`, `0x78`, `0x77`, and `0x3f`/`0x3f`), so it uses the sends as a stereo pair. The control word at the start of each half (`0x0000`, `0x8000`) gives each output group's headroom: bits 12–10 for the direct-stream pair and 8–6 for the rest, the number of bits the 32-voice sum is shifted up before its top 16 bits are taken. The driver writes `0x1aa3`: 6 and 2, so the main and send buses run 24 dB below the direct-stream pair. That is what Half-Life's `0x1f` on those mixer inputs (+17.5 dB, see the mixer law) makes up for. Aureal's description, relayed by the map's author, calls the reverb and chorus outputs a pair of software-fed DirectSound pipes for extra wavetable effects, not a hardware reverb, which fits Half-Life using them as a stereo pair. The 86Box model takes the send fields as linear levels (`0x7f` = full) and the pan field as a linear crossfade (a crossfade per the map's author; the linear scales are Hypothesis). Linear sends make Half-Life's widest pan only about 8.4 dB between the sides (the quieter send goes down to `0x30`), and it is also assumed, not measured, that the reverb send (36) is left. Three attempts to read the law and the assignment from the 11 November real-card tram ride (stereo recording and trace) failed: the voices never play alone, and their balance does not stand out from the A3D sources playing at the same time (correlation with the balance the codes predict 0.1 or less, no peak at the true alignment). A host-side test like run 19, stepping the two send fields under a steady tone on a second-half voice, would settle both. **Settled (Confirmed, wtprobe 2026-11-17):** on an idle card, a second-half voice with `DSREG` clear played a constant from a hand-filled FIFO, and each of the half's outputs was read digitally through a converter at ratio 1. The pan field is a linear crossfade with 0 = output 34 (left) and 0x7f = 35: left falls 12.86 per step from 1620 to about 0, right rises from 0 to about 1600, and the two always sum to the full level (rms 36 and 14 about straight lines). Each send is linear in its field (12.84 and 12.92 per step, 0 at 0, rms 5 and 50) and full scale on a send is the same level as full scale on one side of the main pair; neither send changes with the pan. So the model's linear sends and crossfade are right, and Half-Life's sounds, which go out on 36 (the reverb send, routed to the left mix) and 37 (chorus, to the right), pan by the two send fields alone: a send at 0x30 against one at 0x7f is 8.5 dB, the widest Half-Life uses. Two loose ends: the four outputs also carried a component alternating sample by sample (about ±2,400 on 34, ±1,500 on 35, ±340 on 36, ±2,600 on 37) that did not change with any setting and averages out, its source unknown; and the full level, 1,620 for a 16,384 input at unity gain, is 4 dB above what the model's 24 dB headroom gives (1,024), which needed checking against the direct-stream pair. `wtprobe levels` did that: with `DSREG` set the same voice at pan 0 gave 26,003 on output 32 for a 16,384 input (13,001 for 8,192: linear) and 0 on 33, so the pan acts on the direct-stream pair too; with `DSREG` clear it gave 1,620 on 34. The ratio, 16.05 (24.1 dB), is the headroom difference the model uses. In absolute terms, though, 26,003 is 0.79 of the ×2 that the headroom arithmetic gives for a full-scale voice at gain `0xcf` panned hard to one side, which does not fit run 16's unity at centre pan either (that would need 2.0 × 0.5); `wtprobe gains` and `wtprobe state` then measured the voice's gain chain on the direct-stream pair, with the half's other voices muted (which removes the alternating component):
- **Gain bytes (Confirmed).** Both the gain byte (`PARM0` bits 23–16) and the input gain byte (`PARM3` bits 31–24) decode exactly as the model has them, to the last unit at every code from `0x10` to `0xcf`: 0xce = 0.9667 of 0xcf, 0xc0 and 0xbf both exactly half (the repeated mantissa), 0xb8 = 2,492 against 2,491.6 predicted. Codes above `0xcf` give smaller, irregular values (0xd0 = 0.566, 0xe0 = 0.633 of 0xcf; 0xdf, 0xef, 0xff = 0xcf); nothing uses them.
- **Pan (Confirmed).** Left = (127 − p)/127 and right = p/127 of the full level, on this pair as on the main pair: at `0x3f`, 3,276 and 3,224 of 6,500.
- **Gain state (`PARM3` bits 23–21).** States 0, 1, 2 and 4 are silent; 3 and 7 are full. The 0.812 first read for 5 and 6 was a mute ramp caught part way; `wtprobe ramp` (below) shows 2, 3, 5 and 6 are transient. The driver uses 7 and 0.

**Attack and smooth mute (Confirmed, `wtprobe ramp`, 2026-11-17).** Aureal's description of the two ramps, relayed by the map's author, was tested step by step, watching the voice's output and registers for 0.4 s each (98 cases). Data: `data/wtprobe-ramp-20261117.jsonl`, `.npz`.

- **Ramp periods.** Each ramp register (`MRAMP` at bank + `0x0c`, `ARAMP` at + `0x14`) is a rate added to a 32-bit phase every sample, so a period is 2^32 / rate samples. Mute rates `0x20000000`, `0x10000000`, `0x08000000`, `0x01000000` and `0x00100000` gave mutes of 8, 16, 32, 256 and 4,096 samples; attack rates `0x01060000`, `0x00830000`, `0x00410000` and `0x00030000` at slope 4 gave 125, 250, 504 and 10,921 samples, each as predicted. The driver's values, written once at start-up, are `0x10000000` (16 samples) and `0x00830000` (500 samples, 10.4 ms).
- **Smooth mute.** Writing 1 to the voice's mute word (bank + `0x100` + voice × 4, one word per voice as ALSA has it; setting the voice's bit in voice 0's word did nothing) puts the voice in state 5 and sets both gain bytes to `0xff`. At the next wrap of the mute phase it goes to 6 and the level falls linearly in amplitude to zero over one period (6,500 → 0 in 16 equal steps at the driver's rate); then it goes to 0, the mute word clears and the voice's gain-mode bit is set.
- **Attack.** From hard mute, with PARM0's gain byte holding phase 0 and a slope in bits 2–0 and PARM1's the target gain, writing state 2 makes the voice wait for the next 1/32 of the attack period (0.2 ms here), go to 3 with the interval's number in the phase bits (`0x04` read back as `0xf4`), and rise linearly in amplitude to the target. The rise takes (8 − slope)/8 of the period: 62.9, 125, 188, 250, 314, 372, 433 and 485 samples for slopes 7 to 0 against a period of 500, so slope 7 is the fastest and 0 the full period. At the end the voice goes to 7, PARM0's gain byte takes the target and the gain-mode bit is set. Written directly, state 3 finishes at once; 5 and 6 written directly run their mute; 1 and 4 stay silent and never change. PARM1's bit 0 (which the driver sets) made no difference to an attack, but in one pair of cases it chose the gain for state 7 written directly: with PARM0's byte at `0x04` and PARM1's at `0xcf`, the voice played silent with the bit set and at full with it clear, so the bit appears to pick the base (set) or the target (clear) gain.
- **Gain-mode bits** (bank + `0x10`, one bit per voice) clear when a ramp starts and set when it ends. The Windows MIDI synthesiser polls this word; on a card where no ramp is running it reads all ones, as run 12 saw.

The emulator models all of this (2026-11-17). For the Windows driver nothing changes, since it never uses the ramps; a Half-Life replay matched the previous model to the last bit but for 62 samples off by one.


- **Filter byte.** No effect on a steady level from `0xc0` up; `0xb0` takes 2.6% off.
- **Input level.** Linear from 16 to 16,384 with a factor that creeps from 1.5869 to 1.5871 and a floor-type bias of 1–2 LSB (−4,096 gives −6,502 against +6,500); full scale saturates at 32,767 / −32,768.

So the voice's output is 1.587 × its input at full gain and full pan, 0.794 of the ×2 that the headroom arithmetic gives, and the shortfall is not in any field stepped here. It is close to 2^(−1/3). This sits awkwardly with run 16's analog measurement that a direct-stream voice at `0xcf` and centre pan plays at the level of the plain ADB path; at centre pan the card gives 0.80 per side by this measurement. `wtprobe mix` settled it (Confirmed, 2026-11-17, two runs identical). The same constant from an ADB FIFO and from the voice (direct-stream pair, pan 0, gain `0xcf`) went straight into a converter and, separately, through mixer 0 at unity in and out. The ADB path came through unchanged both ways (4,096 → 4,096), the voice at 1.587 × both ways (4,096 → 6,500; 8,192 → 13,001), so the mixer passes both alike and the factor is the voice's own. The mixer input gain also read exactly as its law gives: `0x00` 0.5, `0x04` 0.75, `0x08` 1, `0x0c` 1.5, `0x10` 2. `restprobe mix` (2026-11-17) took it to the last bit: every input gain from `0x00` to `0x1f` gave floor(x × gain) for values from 1 LSB to full scale and both signs (`0x00` on 3 and −3: 1 and −2; `0x04` on 7: 5; `0x0c` on −1: −2; `0x1f` on 3: 22), saturating at 16 bits; two inputs add and saturate (24,576 + 24,576 = 32,767); the output gain follows the same law. The model now floors each product and its output to the 16-bit step. A direct-stream voice at the driver's centre pan (`0x3f`) therefore plays at 0.80 and 0.79 of the ADB path's level on the two sides (−2.0 and −2.1 dB), which contradicts run 16's analog finding of equal level; the digital reading is taken as the card's behaviour and the emulator now follows it: voice output × 1.5871, the pan crossfade on both pairs, the main pair and sends at 1/16 of the direct-stream pair, and the measured gain states. Against the previous model this makes direct-stream voices 2 dB quieter and main-pair and send voices (Half-Life's ordinary sounds) 4 dB louder; worth an A/B against the period-machine recordings. Data: `data/wtprobe-mix-20261117.jsonl`.

**A voice's own output, and where the factor sits (Confirmed, `wtprobe own`).** The voice's own ADB source (`0x80` + voice in the second half), the route the driver uses to feed an A3D source from a wavetable voice, reads 0.7998 × the input (4,096 → 3,276, 8,192 → 6,552), the same with `DSREG` set or clear and the pan at 0, `0x3f` or `0x7f`, and scaled by the gain byte as decoded (`0xc0` half, `0xa0` an eighth). That one factor explains every level on the mixed pairs once the pan and send fields are read as 0.7 fractions, as the map's author describes them: the direct-stream pair is the voice's sample × 2 × (127 − p)/128 on the left and × p/128 on the right (pan 0: 0.7998 × 2 × 127/128 = 1.5871; pan `0x3f`: 0.7998 and 0.7873, the 3,276 and 3,224 measured), and the main pair and each send are 16 × lower with the send field also /128. Where the 0.7998 comes from was settled by `lastprobe` (2026-11-17): it is `0x3330`/`0x4000` (0.79980) and it rides on the interpolator. A single sample of 16,384 played at step 1 with the pitch phase (`PARM2` bits 15–0) at 0 read back 13,104 (`0x3330`); with the phase set to each of 64 fractions the impulse came back as four weights equal to the cubic Lagrange kernel times that, within 1.6 LSB (at phase ½: −819, 7,371, 7,371, −819), and the driver's 44.1 kHz step (`0x9acc`) gave the predicted impulse response within 5 LSB. So the interpolator is the model's, scaled by `0x3330`/`0x4000`, and the 44.1 kHz image line that recorded 6 dB under the model is not in the chip's digital output. One sample per FIFO word, the low half (an impulse in the high half did not play). Values through the whole voice came out at floor(x × 0.7998) or 1–2 LSB under it, the gain and filter stages each rounding down. Data: `data/lastprobe-20261117.jsonl` and the `interp` and `own` files. The emulator now uses this: the A3D-input route at 0.7998, the pairs as above. Data: `data/wtprobe-own-20261117.jsonl`. The alternating component stayed with the voice silent and is absent on the direct-stream pair, so it comes from the half's other voices, which on a cold card hold their power-up state; it is not part of this voice. - **Base/target smoothing is never used by the Windows driver (Confirmed in traces; mechanism Plausible, register map).** Each voice parameter word (pitch, gain, filter cutoff) has a base copy (`PARM0`) and a target copy (`PARM1`), each with a state bit (bit 0). When the two state bits are equal, the value is base + ramp × (target − base), where the ramp is the half's `SRAMP` word (`0x0004`/`0x8004`: an unsigned 0.16 slope in bits 31–16 added each sample to a 0.16 value in bits 15–0, which stops at 1.0 until software restarts it); when they differ, the value is the base. The driver writes `SRAMP` once (`0x00830000`), and in 155,000 traced `PARM1` writes across Half-Life and the test suite the state bits always differ, so the model uses the base copy. The gain and cutoff bytes are 4-bit-exponent/4-bit-mantissa codes and the pitch a 3-bit exponent with a 12-bit mantissa over the base copy's bits 15–1.
- **Mixer gains above unity amplify (Plausible).** The earlier model saturated mixer gains at `0x0a`, because Half-Life's `0x1f` on the send buses' inputs (+17 dB) swamped the 3D sound when those buses carried the voices at full level. With the buses' headroom the voices reach the mix at about −6.5 dB at full send, and the model no longer saturates. In a render of an 86Box tram-ride session the send buses moved from −30.5 to −39.2 dB against a −16 dB mix, and the mix's balance moved slightly toward the real recordings (left/right correlation 0.28 to 0.25, side against mid −2.0 to −1.7 dB; two real-card sessions give 0.06 and 0.17, −0.5 and −1.4 dB, over different stretches of play). The absolute send level is not yet confirmed on a real card; footsteps and other ordinary Half-Life sounds go this way.
- **What feeds 34/35 is unknown.** No session routes it.

An earlier model treated a set `DSREG` bit as "own source only", which silenced every DirectSound voice: in Drakan that was all the dialogue and most effects.

**Which buffers get wavetable voices (Confirmed, runs 15 and 16).** With A3D open (the test program's default), DirectSound gets four hardware buffers, on ADB channels 3–6; every further buffer is mixed in software into channel 0. With A3D closed, as in a game's DirectSound mode, hardware buffers take ADB channels 1–14 and then first-half wavetable voices; 40 buffers all got hardware. DirectSound 3D buffers start on an ADB channel the same way.

### A3D 3.0 and the driver's reverb (Strong, 86Box sessions of 2026-11-16)

A3D 3.0 is `a3dapi.dll` 3.x (3.12 ships with the Messiah demo) over the same driver; the 4.06.2048 driver is the first to list A3D 3.0, EAX 1.0 and I3DL2 support and a host reverb engine ("A3Dverb"). At the card, a 3.0 program looks like a 2.0 one. Messiah (whose executable carries the `IA3d5`, `IA3dSource2` and `IA3dReverb` interface IDs) and Elite Force wrote to no register block and used no kind of route that Half-Life does not. Aureal's SDK sample for volumetric sources drives the ordinary A3D source parameters and nothing else.

Reverb is the one feature with a path of its own, and it is **off as installed**. The library asks the driver's sound buffer for the EAX 1 and I3DL2 property sets when it starts; if the driver supports neither, `IA3d5::BindReverb` fails (the SDK's `reverb` sample stops with "Failed to bind reverb to A3D"). The driver answers from one registry value, `HKLM\Software\Aureal\Vortex\AU8830\ControlPanel\ReverbEnable`, which the installer writes as 0 (beside it: `ReverbOnAll` 1, `ActiveReverbLevel` 3, a quality level of 0–4). Set to 1, with a restart, the sample binds its reverb and the driver builds a loop through the host:

- the dry source's converter output goes to its A3D source as before and also to a mixer input (`0x69` in this run) on mixers 10 and 11;
- those two mixers feed two converters, which feed capture channel 2 and its alias (sinks `0x02` and `0x22`: a stereo capture stream);
- the driver computes the reverb on the host and plays it on a stereo stream (channel 3) through two more converters into the canceller's fifth input pair (sinks `0x9a` and `0x9f`), so the wet signal joins the output beside the 3D sources without passing through the A3D engine.

The emulator already carried every part of this (capture streams, the alias sinks, the canceller's fifth pair): with the value set, the sample reports "Playing with reverb" and the replayed output decorrelates and rises about 2 dB while the reverb is bound. Since the reverb itself is the driver's code running on the guest's processor, the card's part is only the loop. Not yet compared with a real card, including whether `ReverbEnable` is 0 on a real installation.

**The SDK's 3.0 samples in 86Box.** Each of Aureal's 3.0 sample programs was run with `ReverbEnable` set: reverb presets, EAX 1 reverb through property sets, volumetric sources, manual reflections, geometry reflections and occlusion all ran, on the same blocks and routes as 2.0 programs (reflections on wavetable voices, as before). Static and streamed WAV and MP3 sources play; MP3 is decoded by the library on the guest's processor. With the reverb on, Messiah starts the reverb loop as soon as a level loads and keeps it, with up to seven sources feeding it. None of this had been compared with a real card's output until the session below.

**The 3.0 samples on the real card (2026-11-17, X79 session `20261117-214518-a3d3-samples`).** `REVERB`, `REFLECT`, `PROPSETS`, `POLYGON`, `MANUALRE`, `LOADTEST` and `LOADING` were run in turn, in a guest without `ReverbEnable`: the driver built no reverb loop (no route to capture sinks `0x02`/`0x22` or to the canceller's fifth pair), which is the expected behaviour with the value unset, so the reverb itself is still to be compared. `LOADTEST` crashed and `LOADING` then wrote nothing to the card. The register trace replayed through the model (`v2replay`) reproduced every route-table and mixer read (31,230, none different). To compare levels, the replay was fed the samples' own WAV data at the addresses of each source's DMA pages, so that the reflection voices, which read the same buffer at later offsets, keep their true delays against the direct sound; the main 2D stream was silenced. Against the line-in recording:

- **Occlusion and geometry (`POLYGON`, Strong).** Over the whole run, card and model differ by one constant (the recording chain's gain): the left–right balance correlates 1.00 with a slope of 0.99, level 0.99 with a slope of 0.99, and the spectrum differs by the same constant within 0.3 dB from 50 Hz to 12.8 kHz. No reflections were in use.
- **Manual reflections (`MANUALRE`, Strong).** The program toggles four reflection voices (first-half voices 0–3, sends 36/37, cut-off byte `0xa1`, gain about `0xa5`, delays 14–30 ms). With them off the card matches the model to the same constant. With them on, the reflections match within 0.6 dB from 50 to 400 Hz but roll off more slowly on the card: +1.6 dB at 400–566 Hz, +3.5 at 566–800, +7.6 at 800–1131 and +11 at 1.1–1.6 kHz. A four-stage filter with twice the coefficient of `0xa1` (as `0xb1` would give) fits that difference to 0.45 dB rms. The filter law was measured on a second-half voice playing at 48 kHz (rate `0xa000`); these voices are in the first half and play a 44.1 kHz source (`0x9acc`), so either the half or the rate might change the cut-off. **`wtprobe filtrate` ruled that out:** impulse responses through cut-offs `0xa1`, `0xb1` and `0xc0` on second-half voice 8 and first-half voice 0, at rates `0x9acc` (44.1 kHz) and `0x7a1c` (22.05 kHz), fit a four-stage filter at 0.8–0.96 × the expanded byte, never twice it (the 48 kHz cases were lost: the impulse played before the capture started, as in `wtprobe reso`). The difference is real, though: replaying with three different one-second slices of the source moved it by under 1 dB. It is small against the whole signal (in the 0.9–2 kHz band, switching the reflections on adds about 0.9 dB on the card and 0.1 dB in the model), and its cause is open. The driver rewrites each reflection voice's `PARM0` every 2.4 ms on average, nudging the rate (`0x9aa0`–`0x9af8`) to steer the delay, and no spectral lines at that write rate stand out on the card.
- **Geometry reflections (`REFLECT`)** follow the card's balance (correlation 0.9), but the drum-loop source changes too much from second to second to separate the reflections' level.

**AC-3 is not supported.** A streamed AC-3 source crashed inside `a3dapi.dll` before any audio reached the card. The SQ2500 has no AC-3 hardware (that was the SQ3500's daughterboard), so the library falls back to a software decoder that its own sample says must be unlocked with a key licensed from Dolby, through DirectShow filters the driver package installs. Nothing here depends on the card, no such key is public, and no game is known to have used it; `tools/a3dtest/loadtest.c` tries it only when asked.

**Reverb parameters.** `IA3dReverb` takes either a preset or a custom set. A preset is one of 26 environments, the EAX 1.0 list in the same order (generic, padded cell, room … psychotic), with a volume, decay time and damping: the EAX 1.0 listener properties. A custom set is the I3DL2 listener property list (room, room HF, roll-off, decay time, HF ratio, reflections and delay, reverb and delay, diffusion, density, HF reference) with I3DL2's ranges and defaults. The library passes each to the driver's matching property set.

**"76 hardware 3D channels".** The A3D 2.0 platform guide credits the Vortex 2 with 76 hardware 3D channels, against 8 for the Vortex 1. The chip has 16 A3D sources; 76 is 16 plus 60, which suggests the driver also counts wavetable voices it can only pan (Hypothesis). That would fit Half-Life, whose sounds beyond the A3D sources play on wavetable voices panned with the two send levels. The same guide says reflections are re-ranked by audibility every 100 ms.

The Miles Sound System provider shipped with Elite Force II (`Mssa3d.m3d`, 2003) asks only for the A3D 2.0 interfaces.

### Comparisons with period machines (2026-11)

Two period PCs with the SQ2500 under driver 4.06.2048 were recorded playing Half-Life's opening tram ride, for comparison with 86Box running the same ride. Both recordings came out mono, the two channels identical, despite several cables and inputs; the speaker-mode recording shows it is the sum of the two outputs, not one of them (a single output would show the canceller's 8–12 dB bass boost against headphone mode, and there is none). So they check level and tone, not the stereo image.

- **Athlon XP, GeForce4 MX 440, headphone mode** (USB recorder, from Windows start-up; no CD music). The 86Box recording, rendered again in headphone mode for the comparison, matches the card within about 1 dB from 160 Hz to 10 kHz and is 2–4 dB louder below 160 Hz (Strong).
- **Pentium III 700 MHz, satellites and then headphones** (CD music playing, Windows mixer untouched). The CD balance is under AC'97 codec above. The two modes of the same card, lined up and compared band by band from 110 s on, against the canceller model run the same way (sum of both outputs, satellites minus headphones):

  | Band | Card | Model |
  | --- | --- | --- |
  | 80–160 Hz | −0.1 dB | −2.8 dB |
  | 160–320 Hz | +0.5 dB | −2.2 dB |
  | 320–640 Hz | +0.2 dB | −0.8 dB |
  | 640–1280 Hz | +2.8 dB | +3.4 dB |
  | 1.3–2.6 kHz | +3.0 dB | +3.2 dB |
  | 2.6–5.1 kHz | −0.2 dB | −3.1 dB |

  The canceller's midrange lift in speaker mode is on the card and in the model within half a decibel, and speaker mode is not quieter than headphone mode on the card, which confirms removing the old 5.5 dB speaker-mode cut (Appendix B). The model is 2–3 dB low in the bass and upper treble; with two different play-throughs that is a lead, not yet an error (Plausible).

What these recordings cannot show: the out-of-phase bass the canceller adds (summing the outputs cancels it), and whether the card saturates on Half-Life's loudest moments in speaker mode as the model does. Replaying one 86Box session through the 0.3 and 0.4 models (the old fitted canceller and the decoded one) gave 0.4 4.5 dB louder, much less correlated between the outputs below 160 Hz (0.7 to 0.1), and touching full scale in 13 of 310 seconds (once in 0.3). That is the decoded arithmetic at the driver's levels; it has not been checked against a card at full level.

### Game note: SiN's dropped dialogue and its "reverb engine" (Strong)

SiN with 3D audio on and its reverb engine off drops about every other line of dialogue in the opening cutscene, and cuts other sounds short. Traces of the same scene on the real card (X79 session `20261108-235104-sin-opening2`, SiN 1.00) and in 86Box show the same thing: the game starts and stops its sounds in the same order with the same timing on both, and for the missing lines it never starts a stream at all. During those gaps only the main 2D stream was running; ten or more ADB channels were idle. So the card did not run out of voices, and the emulator matches the hardware. The fault is in the game.

Turning on SiN's reverb engine (SiN 1.11, 86Box) brings the lines back. It is SiN's own feature, not something on the card: the reverb-on trace writes to no register area that the other runs do not, and it uses fewer. What changes is how SiN uses the card:

- **Reverb off (1.00, real card and 86Box):** a hardware buffer per sound. One-shot ADB streams on channels 1–14 (each 1.5–9 s), wavetable voices, and the 3D sources fed from them.
- **Reverb on (1.11, 86Box):** no wavetable voices and no per-sound streams. Four ADB streams (channels 1, 4, 5 and 6) start with the level and run for minutes, each through a converter into one of A3D sources 12–15. SiN mixes its sounds itself into these four streams, which a reverb would need, and so it no longer goes through the per-sound start path that drops lines.

Two things are still unconfirmed: whether SiN 1.11 with reverb off drops the same lines (the runs above differ in version as well as the setting), and the same reverb-on run on the real card. In SiN 1.11, with or without 3D audio, the driver also routes mixers 8 and 9 to ADB sinks `0x82`/`0x83` and runs ADB channel 2 as a capture stream with no route into it. The model does not implement sinks `0x80`–`0x87`; nothing audible appeared to be missing because of it, but it has not been checked on the real card.

### Game note: what Half-Life itself does with volume, CD audio and Doppler (Confirmed, from the 1998 binaries)

Read from the original `hl.exe` and `hw.dll` (and the shipped `a3dapi.dll`, Aureal's A3D Interactive API DLL 2.02, a COM layer over the system `A3D.DLL`):

- **The game never sets the CD volume.** The CD player lives in `hl.exe` and follows Quake's Win32 CD code: `bgmvolume` (default 1) only pauses the CD when set to 0 and resumes it otherwise, through MCI. So on a real card the music-to-game balance comes only from the Windows CD control (the driver's CD mixer-input gain) and the analog chain. The current Steam release has a real music volume of its own, so its balance is Valve's today, not evidence of the card's.
- **Game sound levels go through the A3D API.** `volume` (default 0.7) is applied in the engine's own mixer and also passed to the A3D renderer's main-volume call, which logs "not yet implemented in API". Non-positional sounds reach A3D as one stereo mix, scaled by `s_2dvolume` (default 0.88). Either way the driver sees the result, so a faithful card model reproduces it without knowing these values.
- **Doppler is A3D's own default.** `s_doppler` defaults to 0, but the engine never passes it (or `s_rolloff`) to A3D: its globals call logs "not yet implemented for Doppler or Rolloff". Moving sources such as the tram therefore get A3D's default Doppler shift, which fits the pitch variation seen on the real card while the tram moves.
- **A3D 2.0 geometry is on by default:** `s_geometry` 1, `s_reflect` 1, `s_occlude` 1 (`s_occfactor` 0.25), `s_refgain` 0.34, `s_refdelay` 4, `s_numpolys` 200, `s_verbwet` 0.15, `s_reverb` 1. Archived values in a `config.cfg` override these.

### The driver's HRTF profile files (Confirmed, layout only)

The 4.06.2048 Windows 98 driver package is accompanied by `.hrtf` files ("Ed's Ears" by Ed Riegelsberger, "Paul's Ears"). "Ed's Ears" is the driver's built-in direction table: all 432 left/right filters captured from the driver (see above) match it to within ±2 units, and its ITD block matches the captured ITDs. The captured table and an OpenAL Soft set built from the profile are in `data/hrtf/`; the profile's layout is:

- A 56-byte header: the magic `HRTF`, version `0x00010000`, sample rate (48000, or 44000 in a second copy), a 16-byte GUID, flags (`0x101`, `0x102`, `0`: one per copy), and the grid: 24 azimuths and 11 elevations (15° steps, −75° to +75°), followed by a length-prefixed profile name and author.
- Per copy, a left block then a right block, each 267 filters of 56 signed 16-bit taps (29,904 bytes): azimuth index (12 − azimuth/15) mod 24, times 11, plus (5 − elevation/15), then three extra entries: straight up (identical to the captured up entry), straight down, and a unit impulse.
- After the taps, a count word (534), a zero word, then 267 left-ear and 267 right-ear ITDs as 16-bit values in 1/256-sample units, in the same order as the filters; they match the ITDs captured from the driver to within 0.004 samples.
- "Ed's Ears" has two identical copies (48000 and 44000); "Paul's Ears" has three copies of a different filter set (correlation about 0.05 with Ed's).

How the driver chooses between profiles is not known. An emulator needs nothing from these (the emulated driver loads whichever it uses); a driver replacement such as the DSOAL fork could read them from the user's own installation.

### The SQ3500 daughterboard (not emulated)

The SQ3500 is an SQ2500 with a DSP daughterboard. No SQ3500 has been traced, and none is to hand, so this section records what the SQ2500's traces and a privately shared register map (not redistributed) indicate, and where an emulation would attach. Treat it all as Plausible until an SQ3500 is traced.

**What the DSP is.** The Vortex's parallel-interface block (`0x22000–0x23fff`) is unused on the SQ2500. The map describes it as a host port for an external DSP and a modem: a window of eight byte-wide DSP registers at `0x22020–0x2203c`, wait-state, DMA (16- or 24-bit words, optional throttling on a GPIO pin, optional polling of a transmit-empty flag before each write), reset, pin and state-machine registers at `0x22040–0x22058`, GPIO routing at `0x2205c` (DSP interrupt and DMA request on GPIO pins, a host-enable strobe on GPIO 1), and a 4 KB window at `0x23000` aliased to one data register, for downloading blocks to the DSP by CPU writes. The eight-register window, the 24-bit words, the transmit-empty flag and the host-enable strobe are the shape of the Motorola DSP56300 family's 8-bit host interface (HI08), so the daughterboard is most likely a 56300-family part. The routing has a destination for the interface (`0xa4`) and a sample-rate header for its DMA (header 21), and the interrupt status word has two bits for the DSP (bits 10 and 11 of `0x2a000`).

**The SQ2500 driver probes for it at start-up (Confirmed in traces; reading Plausible).** Every traced boot does the same short sequence:

| Access | Value | Reading |
| --- | --- | --- |
| write `0x22040` | `0x24`, later `0x1880` | interface wait states (`0x24` is the map's setting for Motorola parts) |
| write `0x22044`, `0x22048`, `0x2204c` | 0 | 16-bit DMA, DMA off, interface reset |
| write `0x22020` | `0x80`, then 0 | DSP register 0 (HI08's interface control register, whose bit 7 is the initialise bit) |
| write `0x22034`, read it back | 0, reads `0xff` | DSP register 5 (a data register): nothing holds the value, so no DSP is fitted |
| read/write `0x2205c` | `0x138015` / `0x138014` read, `0x13801d`, `0x1380dd` written | GPIO routing and pin values |

So `0x22034` reading `0xff` is an empty bus, not a read-only register. That explains the finding above: a register that holds its value tells the driver a DSP is present, and it then spends thousands of writes trying to talk to it and sets aside resources for it (Minerva found 7 stereo 3D sources instead of 9).

**Where an emulation would attach.** The 86Box device already returns `0xff` from the DSP window, which is the SQ2500. An SQ3500 option would add:

1. a DSP56300-family core behind `0x22020–0x2203c` (the maintained open-source core is the one used by the gearmulator project, under the GPL v3);
2. the interface's DMA, fed through routing destination `0xa4` and sample-rate header 21, and its CPU download window at `0x23000`;
3. the DSP's interrupt and request lines through the GPIO routing at `0x2205c` to bits 10 and 11 of the interrupt status word;
4. the DSP's firmware, and how the driver uses it.

Items 1–3 can be built from the map. **The firmware ships with the retail driver:** the Windows 9x 4.06.2048 package installs `stratdsp` (17,419 bytes, version string `v1.13`, copied by `au30mmed.inf`). Its contents are DSP56300 machine code in big-endian 24-bit words (it opens, for example, with immediate writes to on-chip peripheral registers, the usual 56300 start-up), which supports the 56300 identification. Like the HRTF profiles, an emulation would load it from the user's own driver install rather than redistribute it. What it does, and how the driver drives it after the download, would need either static analysis of the driver's VxDs or traces of an SQ3500.

### Clocks, interrupts and DMA

- **Master clock (Confirmed).** `SMP_TIME` (`0x29198`) counts at 12.288 MHz, which is 256 × 48 kHz (measured: 12,288,079 Hz against the host clock).
- **Clock source and a cold card (relayed by the map's author; Confirmed in part).** The chip runs from a 49.152 MHz crystal on its `XTAL_IN` pin (4 × 12.288 MHz) and supplies the AC'97 codec's clocks; it does not take its clock from the codec. A cold card reads `PCI_GCR` (`0x2a00c`) as `0x00303260`, and on the X79 host nothing ran (converters, mixers, wavetable voices) until bit 21 was cleared, which `srcprobe.py release` does along with ALSA's codec-link start-up; the Windows driver leaves the register at `0x01103260`, also with bit 21 clear. The map's author's DOS driver needs no codec at all: it stops all VDB transfers, soft-resets the codec with its clock off, soft-resets the chip (bits 23 and 20 of `PCI_GCR`, then waits for bit 23 to clear), writes `PCI_GCR` = `0x0010326f` (bit 21 clear), clears the status and interrupt-control registers, zeroes or presets each block's RAM (FIFO controls, FIFO triggers, A3D, mixer gains to mute, routes to end-of-list, converters, DMA, EQ), sets the parallel interface's GPIO off, the FIFO triggers to `0x7f`, the DMA engine control to `0x15380000` and the game port to analog mode. So bit 21, not the codec link, is what held the cold card still; the X79 tests changed both at once and do not separate them.
- **Timer (Confirmed).** Writing N to `0x2919c` schedules one timer interrupt N samples (N × 256 master clocks, N × 20.83 µs) later; it is one-shot, and the driver rewrites it in every interrupt. Over 16,000 periods, the card-time from the write to the next interrupt was 257–260 master clocks per unit, the excess being handler latency under QEMU. The Windows driver asks for about 2,345 samples (49 ms, about 20 interrupts per second) when idle and about 236 samples (4.9 ms, about 200 per second) while sound plays. Reading `0x2919c` returns bit 31 set when the timer has fired; the read acknowledges it.
- **Interrupt bits.** `IRQ_SOURCE` read `0x5000` at almost every interrupt (19,508 times). Bit 12 is the timer: the handler masks it in `IRQ_CTRL` (`0x31024` → `0x30024`) while servicing and unmasks it afterwards (Strong). Bit 14 is always set during operation and is not in the mask. The register map names it the modem request, a read-only level that reads 1 while a request is pending (Plausible, register map); it belongs to the parallel interface's modem side (BAR2), which has nothing fitted on the SQ2500 and is never serviced. Bit 2 appeared in 7 of 19,515 reads; the map names it a register-bus time-out error, a pulse, readable and writable (Plausible, register map), which fits ALSA's treating the low byte as error flags. The handler then writes 0 to `IRQ_SOURCE`.
- **Late interrupts (relayed by the map's author, from his own experiments).** An interrupt serviced late is handled like one on time: nothing stops or is flagged, and the driver goes on processing what the A3D library has sent it. What lateness does cost is DMA: a page the driver has not refilled in time plays anyway, which shows up as audio artefacts and as left and right swapped. The emulator's DMA ring keeps playing in the same way.
- **ADB DMA.** Per channel: four page addresses (`BUFBASE`, `0x27400` + channel × 0x10), a configuration pair (`0x27800` + channel × 8), `CTRL` (`0x27a00` + channel × 4: offset bits 0–11, interrupt enable bit 12, direction bit 13, format bits 14–17) and status (`0x27e00` + channel × 4). The driver uses 4 KB pages (size field `0xfff` = size − 1) in a four-page ring and rewrites page addresses as playback advances. DMA interrupts stay disabled; the driver polls positions from the timer interrupt instead. Format codes 1 and 8 were seen; their meaning is unconfirmed.
- **Wavetable DMA** has the same structure at `0x27000`, `0x27600` and `0x27900`.

## Implications for an emulator

An emulated Vortex 2 can run Aureal's original Windows drivers and A3D API unmodified, so everything the driver computes on the host, which includes the HRTF filters, comes along for free. The device itself has to reproduce the chip, not the A3D algorithms. The model in `core/` (the same code as the 86Box device) does all of the following; it has no 86Box dependencies.

The model, in the order it was built:

1. **PCI device** with the IDs, BAR sizes and config-space defaults in PCI identity.
2. **Register file** of 256 KB with the reset values from the cold read, `0xDEADBABE` in decoded gaps, and last-value-read behavior from `0x2c000` up. Expose it through both BAR0 and the BAR1 index/data window.
3. **AC'97 codec** answering as a STAC9708/9711 through `CODEC_IO`.
4. **Interrupts, timer and DMA**: `IRQ_SOURCE`/`IRQ_CTRL`/`STAT`/`CTRL` at `0x2a000–0x2a00c`, the timer at `0x2919c`, the sample counter at `0x29198`, and the WT and ADB DMA engines at `0x27xxx` with their position and status registers.
5. **Audio path**: FIFOs, the ADB routing table (`0x28000`), sample-rate converters (`0x26xxx`), the mixer, whose current gains take their targets at the signal's next zero crossing (`0x20000–0x21fff`), and the wavetable voices (`0x00000–0x0ffff`), which also carry reflections.
6. **A3D per source**: a 56-tap FIR per ear (right = upper halves, left = lower halves), an ITD delay, a gain and a biquad atmospheric filter, each gliding from current to target values. Then the speaker crosstalk canceller and hardware EQ.

Traces serve as a regression suite: `v2replay` replays a trace's register writes into the model and compares the model's answers to the driver's reads with what the card returned ([Appendix C](appendix-c-workflow.md)).

## Open questions

The major gaps, roughly in order of what an emulator needs first:

- [x] **Timer and interrupts**: the timer (N samples, one-shot), master clock (12.288 MHz), DMA page ring and timer interrupt bit are measured. `IRQ_SOURCE` bit 14 (modem request) and bit 2 (register-bus time-out) are named by the register map, and late servicing is handled like on-time servicing, with DMA misses giving artefacts and swapped channels (relayed; see Clocks, interrupts and DMA). Neither bit matters to the driver as traced.
- [x] **The routing graph** the Windows driver builds for WAV and A3D playback (see Routing). Still to capture: recording, S/PDIF and DOS modes.
- [x] **Sample-rate converter internals**: `CONVRATIO`, Doppler, pitch and DMA format codes are decoded, and the 27-point filter was read from the card's impulse responses (runs 12 and 16); for emulation that is the whole converter. The coefficients are now read off the card digitally (srcprobe, 2026-11-17): a Kaiser-windowed sinc, β 7.70 over a half-width of 12.85 samples, fits every measured tap to 0.65 LSB of a 16384 impulse. What is left for bit accuracy is how the chip stores and interpolates them (a table between phases or computed) and their word length; a sweep with a full-scale impulse would show the last bits. Two smaller gaps: the `U0–U3` and drift words, which the driver writes and the model ignores without any measured difference (`U0`'s low byte is `0xc0` plus the converter number), and conversion from input rates above 48 kHz, which no traced program asked for.
- [x] **A3D arithmetic**: done (test-suite runs 1–4, the glidewatch readback and run 12). Gain and taps are Q15 at unity scale, ITD is in 1/512-sample units, and the atmospheric filter is a double real pole. The direction table (15° × 15°) is captured, and the driver interpolates it bilinearly in azimuth and elevation: 351 positions on a 3.75° grid in three regions matched bilinear interpolation of the table to within 0.05% (rounding), against 7–16% for nearest-point or one-axis schemes. Glides step every 64 samples with time constants 2²¹ / TC (gain, filter, HRTF) and 2¹⁹ / TC (ITD).
- [ ] **Wavetable engine**: the voice words are decoded, and the rate, interpolation, gain codes and four-stage filter are measured (runs 18 and 19). The pan field is a crossfade pan, and the attack and smooth-mute ramps are measured and modelled (`wtprobe ramp`; the Windows driver never uses them). The resonance word is decoded (a ladder, k = (−word mod 2^16)/2^14). Still open: the send scales and which send is left (settled by wtprobe: linear sends, 36 is the reverb send); and what decides which sounds the driver puts on wavetable voices. One image line at 44.1 kHz recorded 6 dB below the interpolation model, 61 dB under the tone; the chip's digital output matches the model (`lastprobe`), so the difference is in the analog path or the recording.
- [x] **Crosstalk canceller**: arithmetic decoded and confirmed against a real card for all three presets, level and delay included (Appendix B). Not bit-exact: the chip's fixed-point rounding and error feedback are not reproduced, and the enable bit is ignored.
- [x] **True power-on state**: read after a full power-off (2026-10-30); memory regions power up random, fixed patterns and control registers as listed under Address map.
- [ ] **Legacy DOS support**: Sound Blaster in a DOS window is software emulation by the Windows driver over the normal playback path (see DirectSound buffers and the mixer). MIDI through the "Wavetable" device is host software synthesis (run 12). BAR2 is the parallel interface's modem port (see PCI identity). Still open: real-mode DOS. The MPU-401 and game port are well understood (ALSA drives both) but have not been traced on the card or emulated. What the traces do show: the Windows driver writes CTRL2 (`0x2880c`) = `0x6100` (MIDI clock divider `0x61`) at start-up and, in run 12, sets the low bits of `PCI_GCR` to `0x6f` (ALSA: MIDI enable, game port enable, MIDI port field 3 = `0x330`, plus bits 1–2) with game port field 1. It never touches the memory-mapped MPU-401 or game registers (`0x28800`–`0x2881c`), so its MIDI and joystick traffic goes through the legacy I/O ports, which QEMU's vfio does not pass to the card; that is why none of it appears in a trace or works in the VM. `tools/legacyprobe.py` tests both from the host (Confirmed, 2026-11-17, nothing plugged in):

- **The MPU-401 is a real UART at its memory-mapped registers.** Reset (`0xff` to `0x28804`) and UART mode (`0x3f`) each put the acknowledgement `0xfe` in the data register (`0x28800`). Status bit 7 is set while there is nothing to read (`0x80` idle), as on an MPU-401; bit 0 came on with UART mode (`0x81`). Bytes written back to back went in at once for the first 17, then one every 316 µs: a 16-byte transmit FIFO plus the shift register, draining at 31,650 baud. That is the 49.152 MHz crystal divided by 16 × the driver's divider `0x61` (97), 31,670 baud, 1.3% fast, inside MIDI's tolerance; the divider sits in CTRL2 bits 15–8. Nothing came back on MIDI in (nothing was connected), and no interrupt-source bit was set by the traffic. A scale played for anyone listening on the game port's MIDI pins or the header.
- **The game port reads as unplugged.** The legacy byte read `0xf0` at rest (buttons up, one-shots idle); after a trigger write all four one-shots stayed high for 20 ms (no stick to time them out). In ADC mode (CTRL2 bit 6) the four axis words read `0xffff`, full scale.
- **Legacy I/O.** The first run (2026-11-17) found nothing at `0x300`–`0x33f` or `0x200`–`0x20f`, probably with I/O space off in the card's PCI command register, which the legacy decodes need (see the FM section; that run did not log it). Rerun with it on (2026-11-18, `legacyprobe ports`, COMMAND `0x3`): **the MPU-401 answers at `0x300 + 0x10 × field`** for all four values of bits 6–5 (`0x300`, `0x310`, `0x320`, `0x330`), status `0x80`, `0xfe` after a reset (Confirmed). The game port still answered nowhere at `0x200`–`0x207` with bit 3 on, and `220h`–`22Fh` stayed `0xff` with every control-word bit tried (`sbprobe sbon`), while `330h` and `388h` reach the card on the same machine. Both are most likely held by this chipset (the X79's LPC bridge can decode the game-port range itself); the Sound Blaster ports may also need something AU30DOS sets outside the control word (Open).

**The wavetable header.** The SQ2500 has a Wave Blaster header (dosdays.co.uk lists it among the card's features); on the board it is JP1, the 2 × 13 header near the edge connector (a 2008 VOGONS post places a daughterboard there). JP2 (2 × 10) and JP3 (2 × 13) beside the AU8830 are for the SQ3500's DSP board. Reports of daughterboards working on the SQ2500 are mixed on VOGONS: some work with the "Vortex AU8830 MPU-401" device selected, others stayed silent. A Wave Blaster board takes its MIDI from the card's MPU-401 transmit line and returns analog audio, which on Vortex 2 cards is reported to enter through the codec's auxiliary input; neither has been checked electrically on this card. For an emulator this means the header needs nothing of its own: 86Box's MPU-401, mapped where the driver enables it and on `0x28800`/`0x28804`, sends to whatever MIDI device the user has chosen (FluidSynth with an SF2, an MT-32 emulator, or a real port), which stands in for a daughterboard. 86Box does this (2026-11-17): its MPU-401 in UART mode and its game port follow the enable bits of `PCI_GCR`, and the chip's own registers at `0x28800`–`0x2881c` reach them too; the MPU-401's interrupt is the chip's `IRQ_MIDI` source (`0x2000`). The MIDI port field takes 3 = `0x330` from ALSA and the game port field 1 = `0x201` by assumption; the other values of both fields are guesses until a machine that forwards legacy I/O to the card can read them. A wavetable daughterboard on the card's header is outside the chip: its audio is wired to the codec, and the map's author believes its MIDI comes from the chip's auxiliary serial port (channel 0 or 1); not tested.
- [ ] **Bit accuracy**: the chip's fixed-point word lengths, rounding and saturation in each block, and its internal tables (the converter's coefficients, the expansion of gain codes), have not been recovered. They could be read out with crafted inputs and register settings. The 3D path's level is settled: the slices' outputs are halved after a 16-bit clip, the canceller and mixer are as modelled, and a constant through the driver's whole 3D and native paths read on the card exactly as the arithmetic gives (`pathprobe`); the factor of 0.75 once applied was an arithmetic slip and is gone.
- [ ] **Coverage**: other driver versions (such as 2041), Windows 2000 and XP drivers, A3D 1.0 titles, two-channel boards (SQ1500, Montego II), S/PDIF and the SQ3500 DSP daughterboard. A3D 3.0's reverb, volumetric sources and manual reflections have run in 86Box but not been compared with a real card, and the card's own speaker-mode level on loud game passages is unmeasured.
